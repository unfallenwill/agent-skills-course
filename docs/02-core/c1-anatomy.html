S2 读懂规范

Skill 的解剖：目录结构与 SKILL.md

一个 Skill 就是一个目录，最少只需要一个 SKILL.md。看清必选与可选的每一部分，以及正文该怎么组织。

阶段：S2 读懂规范 · 建议 30 分钟 · 先修：渐进披露

[本课程观点] 规范其实很短：一个目录，一个必选文件，最多再加三个约定目录。真正需要花时间的是正文——它决定 Agent 能不能把事做对。

目录结构

[规范] 一个 Skill 是一个目录，至少包含一个 SKILL.md 文件。目录还可以包含任意其他文件与目录；规范约定 scripts/、references/、assets/ 三个可选目录用于组织常见内容。（来源：specification.md）

my-skill/
├── SKILL.md          # 必选：元数据 + 指令
├── scripts/          # 可选：可执行代码
├── references/       # 可选：参考文档
├── assets/           # 可选：模板、静态资源
└── ...               # 其他任何文件或目录

目录名不是随便取的：name 字段必须与父目录名完全一致。也就是说，pdf-form-filler/SKILL.md 里的 name 必须是 pdf-form-filler。[规范]（specification.md）这条规则会在下一课展开。

[规范] 目录结构看似简单，实际决定了三件事：客户端能否发现技能、相对引用能否解析、以及技能能否被整体复制。父目录名与 name 一致，不只是校验规则，也是客户端用目录归属技能的依据。三个可选目录只是约定，不是白名单；你可以放任意文件，但把它们放进 scripts、references、assets 能让读者一眼判断用途，也方便按需加载。不要为了“看起来规范”创建空目录，空目录不会带来任何加载收益。

[规范] 另一个常见问题是把技能放在项目根目录之外，或者目录层级多套了一层。客户端通常只扫描特定位置的直接子目录，例如 .agents/skills/roll-dice/。如果你写成 .agents/skills/my-skills/roll-dice/，多出来的中间层会让技能无法被直接发现。移动目录后要同步检查 name，避免出现“文件能打开但校验失败”的情况。

SKILL.md 由两部分组成

  1. YAML frontmatter：文件最开头，由两行 --- 包围的键值块。至少包含 name 与 description。
  2. Markdown 正文：第二个 --- 之后的所有内容。没有格式限制。
---
name: roll-dice
description: Roll dice using a random number generator. Use when asked to roll a die (d6, d20, etc.), roll dice, or generate a random dice roll.
---

To roll a die, use the following command that generates a random number from 1
to the given number of sides:

```bash
echo $((RANDOM % <sides> + 1))
```

Replace `<sides>` with the number of sides on the die (e.g., 6 for a standard
die, 20 for a d20).

上面是来源快速入门中的完整例子。注意它没有：解释什么是骰子、介绍随机数原理、列出所有可能的桌面游戏。它只写了 Agent 不知道的一件事——用哪条命令、怎么替换参数。这是“上下文经济”的最简示范。[规范]（quickstart.md）

[规范] frontmatter 与正文的边界要严格：第一个 --- 必须在文件开头，第二个 --- 单独成行，之后才是正文。frontmatter 里的值如果包含冒号或井号，要加引号或使用块标量；正文里则可以自由使用 Markdown、代码块和表格。解析器只关心元数据块，不理解正文；因此不要把关键触发信息只写在正文第一段里，客户端在发现阶段看不到它。正文可以写得很长，但规范建议控制在 500 行以内，并把低频细节移到支持文件。

[规范] 写作时可以先只写 frontmatter 和三条流程，运行一次，确认技能能被发现、能触发，再补细节。这样能把“格式错误”和“内容不好”两类问题分开排查。如果一上来就写 300 行，最后触发失败时，你很难判断是描述没写对，还是 YAML 解析失败，抑或客户端根本没扫描到目录。

正文写什么

[本课程观点] 规范没有强制结构，但给出三个推荐部分：

  • 分步指令：按执行顺序写，步骤之间不要藏隐含依赖。
  • 输入与输出示例：一个真实输入、一个期望输出，比十句形容词更能约束格式。
  • 常见边界情况：空文件、缺列、重复键、编码错误、权限不足。写成具体现象与处理方式。

[本课程观点] 本课程建议的正文骨架（不是规范要求）：

# 技能标题（可选）

## 何时使用 / 不适用
一句话边界，帮助模型避免误用。

## 前置检查
必须存在的文件、命令、权限；缺失时怎么办。

## 流程
1. ...
2. ...
3. ...

## 输出格式
一个模板或一个真实示例。

## Gotchas
- 具体字段/命令/边界的坑，每条都能对应一次真实错误。

## 验证
运行什么命令、看到什么算通过。

[本课程观点] 这个骨架覆盖了“开始前—执行中—结束后”三个阶段。它不适用于所有技能：一个纯知识型技能可能只需要“判断规则 + 示例”，一个脚本编排型技能可能需要更详细的错误处理。骨架是起点，不是模板。

[本课程观点] 骨架的价值在于顺序，而不是标题本身。前置检查放在流程前，能让 Agent 在动手前发现缺少文件或权限；验证放在最后，能让“完成”变成可检查的状态。Gotchas 最好紧跟流程，因为模型在执行中最容易犯的就是这些具体错误；如果放到文末，它可能读不到就开始了。输出模板可以内联，也可以放 assets，但必须在生成结果之前被引用。每个小节都应该能回答“如果没有它，会在哪一步出错”。

三个可选目录的分工

目录放什么什么时候读/执行注意
scripts/可执行代码，如校验器、解析器、转换器流程执行到对应步骤时应自包含或明确依赖；要有帮助信息与错误处理
references/详细技术参考、表单结构、领域规则指令明确要求时单个文件保持聚焦；文件越小，按需加载越省
assets/模板、图片、查找表、schema需要套用模板或查表时是静态资源，不是指令；不要指望模型自动理解图片

[规范] 规范对三个目录的说明：scripts/ 中的脚本应自包含或清楚记录依赖，包含有帮助的错误信息，并优雅处理边界情况；references/ 用于 Agent 在需要时阅读的额外文档，建议保持单个文件聚焦；assets/ 存放模板、图片、数据文件等静态资源。（来源：specification.md）

[规范] 三个目录的选择可以用一个问题判断：这份内容是让 Agent“知道”，还是让 Agent“执行”？知道且每次都要，放正文；知道但偶尔才要，放 references；需要确定性执行，放 scripts；需要被套用或填充，放 assets。分类不清时，优先看加载成本：脚本通常只在某一步运行，不会整份读入上下文；参考文件会被读入，所以要控制大小；模板和图片通常只被引用，不进入推理。把它们混在一个目录里，会让按需加载失去意义。

[规范] 还有一条实用规则：不要让脚本依赖 assets 里的相对路径而不说明。Agent 执行命令时的工作目录未必是技能目录，脚本应该接受显式路径参数，或在内部基于自身位置解析。正文里写“scripts/extract.py”是给读者看的相对引用，不等于 shell 的工作目录。把这两件事分开，能避免大量“本地能跑、Agent 跑不了”的问题。

文件引用：相对路径，且只深一层

[规范] 在 SKILL.md 中引用其他文件时，使用相对于技能根目录的路径：

详细字段说明见 [references/fields.md](references/fields.md)。

运行提取脚本：
scripts/extract.py

规范建议把文件引用保持在一层深度，避免深层引用链。[规范]（specification.md）原因很实际：如果 A 指向 B、B 又指向 C，Agent 需要连续做两次“是否要读”的判断，漏读概率上升，定位成本也上升。

路径陷阱

[规范] 脚本里的路径和正文里的引用是两回事。正文中的 references/fields.md 相对于技能目录；脚本中的路径通常相对于当前工作目录，而 Agent 运行命令时未必在技能目录下。稳妥做法是让脚本接受显式路径参数，或在脚本内部基于自身位置解析。

[规范] 引用路径的基准是技能根目录，而不是当前工作目录，也不是 SKILL.md 所在的系统绝对路径。规范建议保持一层深度：SKILL.md 直接指向 references/fields.md，而不是让 fields.md 再指向更深层的文件。深链的问题不是“不允许”，而是每多一层，模型就多一次判断，漏读和读错的概率都会上升。文件名也应该承担导航作用，fields.md 比 doc2.md 更容易被正确选择。

一个带支持文件的完整结构

release-notes/
├── SKILL.md
├── references/
│   └── style-guide.md      # 团队措辞与分类规则
└── assets/
    └── template.md         # 发布说明模板

[本课程观点] 对应的 SKILL.md 只需要写清：何时生成发布说明、从哪里取变更、如何分类、套哪个模板、写完如何自检，以及“当需要调整措辞时，读 references/style-guide.md”。模板本身放在 assets，不占正文。这样做的效果会在教程 2中被实际测量。

[本课程观点] 这个结构的关键不是“有三个目录”，而是每个文件都有明确的加载时机。主文件写流程与判断，style-guide 只在需要调整措辞时读，template 只在生成最终文本前套用。你可以用一张纸画出这三者的关系：哪一步需要哪个文件，读完它解决什么问题。如果画不出来，说明结构还停留在“分类”，没有进入“调度”。真正的渐进披露，是让模型在正确的步骤看到正确的内容，而不是把文件整齐地摆在那里。

[本课程观点] 用一个你熟悉的真实材料照这一节做一遍：先保留必须的字段与判断，再删掉模型已知的解释，最后补一个别人能执行的验证。完成后让同事只看结构，判断他能否说出何时该读哪个文件。

如果你只记住三件事

  1. Skill 是目录，SKILL.md 必选；scripts / references / assets 是可选约定，不是必需。
  2. SKILL.md = YAML 元数据 + Markdown 正文；正文唯一的目标是让 Agent 做对，而不是写全。
  3. 引用用相对路径，保持一层深度；路径解析基准是技能根目录，不是当前工作目录。

练习

基础

[本课程观点] 列出创建一个最小可用 Skill 所需的全部文件，并指出哪些是可选的。

提示与自检

[本课程观点] 必需：<skill-name>/SKILL.md，其中包含 name 与 description。可选：scripts/、references/、assets/ 及其他任何文件。若你答“还需要 manifest.json 或 package.json”，那是别的工具链，不是 Agent Skills 规范。

基础

[本课程观点] 回到本页第一个概念小节，用两三句话说明它解决什么问题，并举一个你工作中会遇到的例子。

提示与自检

[本课程观点] 合格答案要包含“问题—做法—具体场景”三部分；只复述小节标题，或举一个与本页无关的例子，都不算完成。

进阶

[本课程观点] 一个技能正文引用了 references/a.md，而 a.md 又让你读 references/b.md。这样设计有什么问题？给出两种改法。

提示与自检

[本课程观点] 问题：形成两层引用链，增加漏读与定位成本。改法一：把 b.md 的关键内容合并进 a.md；改法二：让 SKILL.md 直接按条件引用 b.md，保持所有引用都从主文件出发、只深一层。

进阶

[本课程观点] 把本页的方法用到你自己的一个真实任务上，写出两条可执行指令和一个别人能照着做的验证方式。

提示与自检

[本课程观点] 两条指令要具体到字段、命令、阈值或判断标准；验证方式必须给出可观察的结果，例如某个文件存在、某条命令退出码为 0、某个字段等于期望值。

挑战

[本课程观点] 为一个“把会议录音转成行动项”的技能设计目录结构。指出哪些内容必须留在 SKILL.md，哪些应进 references 或 assets，并为每个支持文件写一句加载触发。

评分点
  • 完整回应题目中的两个关键要求：2 分
  • 给出可验证的检查、示例或对照：2 分
  • 说明一个取舍、边界或失败情况：1 分
