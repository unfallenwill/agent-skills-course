规范与机制/规范

S2 读懂规范

校验、兼容性与常见坑

用 skills-ref 校验、理解严格规范与宽松实现的差别，并逐项排查 name 不匹配、描述缺失、YAML 解析失败等高频问题。

阶段：S2 读懂规范 · 建议 25 分钟 · 先修：生命周期

[本课程观点] 规范只有六个字段，但失败往往发生在这几行里：名字少了一个连字符、描述为空、YAML 里多了一个冒号。这一页把校验做成可执行的动作，并列出一张排查表。

用参考库校验

[规范] 来源推荐 skills-ref：

skills-ref validate ./my-skill

它会检查 frontmatter 是否合法、是否符合命名约定。[规范]（specification.md）参考库位于 github.com/agentskills/agentskills/tree/main/skills-ref。按参考库的安装说明使用；本课程不要求你联网安装，下面的本地脚本覆盖了规范中的硬性字段检查。

[规范] 校验的价值在于把“看起来对”变成“解析器认可”。它会按规范检查 frontmatter 的字段、name 的字符与长度、name 与父目录是否一致等硬性条件。它不会判断描述是否覆盖了正确的场景，也不会判断正文是否有效，因此校验通过不能代替评估。反过来，校验失败必须先修，因为格式不合法的技能可能在发现阶段就被跳过，后面所有评估都无从谈起。把校验放在每次提交前，成本很低，收益很直接。

[规范] 如果团队使用多个客户端，还要做一次跨客户端冒烟测试：在目标客户端里确认技能出现在列表中、能被激活、能读到支持文件。校验器只认识格式，不认识客户端的扫描路径与权限模型。两者都通过，才能说“这个技能在目标环境里可用”。

本课程的零依赖校验脚本

[本课程观点] 仓库 tools/validate-skills.js 用 Node.js 写成，无第三方依赖。它解析每个 SKILL.md 的 frontmatter，检查 name 与 description 是否存在、类型是否为字符串，校验 name 的字符集、长度、连字符规则与父目录一致性，并检查 description 长度。用法：

node tools/validate-skills.js examples

[本课程观点] 输出形如：

PASS  pdf-form-filler        name_ok  description=286 chars  fields=name,description,license,compatibility,metadata
PASS  code-review            name_ok  description=241 chars  fields=name,description
...
SUMMARY  skills=7  passed=7  failed=0

脚本不是官方工具，也不替代 skills-ref；它只覆盖本课程用到的字段与硬性规则。遇到它没覆盖的字段（例如 allowed-tools 的语义），仍以规范和参考库为准。[本课程观点]

[本课程观点] 本地脚本覆盖的是本课程用到的字段与常见 YAML 错误，它故意保持零依赖，方便在离线环境和 CI 中运行。它不是官方工具的替代品：官方工具会跟随规范更新，本地脚本则需要手动维护。一个实用的组合是：日常迭代用本地脚本快速反馈，提交前跑官方工具做最终门禁。脚本报错时，先看它指出的具体行号与字段，再决定是修内容还是修脚本；不要为了让脚本通过而修改期望值。

[本课程观点] 把这一节放回真实任务检验：找一个会用到它的决定，写出遵守与不遵守两种做法，并指出不遵守时会出现什么可观察的错误。写不出具体错误，说明还需要更具体的场景、字段或命令。

严格规范与宽松实现

[规范] 规范采用严格校验（strict validation），客户端实现往往宽松。来源明确描述了两者的差异：

情况规范要求宽松实现的常见行为
name 与父目录不一致不合法警告，仍加载
name 超过 64 字符不合法警告，仍加载
description 缺失或为空不合法跳过该技能，记录错误
YAML 完全无法解析不合法跳过该技能，记录错误

[规范] 实现指南称这种做法为宽松校验（lenient validation）：对不影响功能的问题警告但仍加载，对无法披露的技能则跳过。它还建议对“未加引号但包含冒号”的 YAML 做兜底重试，以提高跨客户端兼容性。（来源：adding-skills-support.md）

不要把“能加载”当成“正确”

[规范] 宽松实现会掩盖问题，直到你换一个客户端或上传到技能市场才暴露。把 skills-ref validate 当作提交前的必跑步骤，就像提交代码前跑测试。

[规范] 宽松实现的好处是兼容旧技能，坏处是掩盖问题。一个 name 与目录不一致的技能，在本地可能照常加载，换一个客户端或上传到市场时才失败；一个 description 为空的技能，在某个实现里可能被跳过，用户只会看到“技能不见了”。因此，不要用“我的客户端能用”作为合格标准。把规范当作下限，把客户端行为当作运行时差异，二者分开判断，排查会清晰很多。

[本课程观点] 把这一节放回真实任务检验：找一个会用到它的决定，写出遵守与不遵守两种做法，并指出不遵守时会出现什么可观察的错误。写不出具体错误，说明还需要更具体的场景、字段或命令。

常见错误排查表

[本课程观点] 排查这张表时，先按“技能有没有出现”分层，而不是逐条试。列表里完全没有：优先查目录层级、文件名大小写、客户端扫描路径。列表里有但带警告：查 name 与目录是否一致、是否超长或含非法字符。列表里没有且日志报解析错误：查 YAML 的冒号、井号、Tab 与缩进。列表里有、能激活，但行为不对：问题已经不在格式，转到描述与正文评估。把问题分到正确的层，能避免在错误的地方反复修改。

[本课程观点] 第二层是“出现了但不好用”。这时要区分触发问题和执行问题：该触发没触发，回到描述评估；触发了但输出不对，回到正文与脚本。第三层是“能跑但不可移植”，通常与路径、编码、依赖和客户端差异有关。每一层都有不同的证据来源：客户端日志、校验输出、触发记录、执行轨迹。先确定层级，再选证据，排查效率会高很多。

[本课程观点] 把这一节放回真实任务检验：找一个会用到它的决定，写出遵守与不遵守两种做法，并指出不遵守时会出现什么可观察的错误。写不出具体错误，说明还需要更具体的场景、字段或命令。

跨客户端兼容性

[本课程观点] 同一个 Skill 目录在支持该格式的客户端之间通常可以复用，但以下方面可能不同：

  • 扫描位置。 有的客户端读 .agents/skills/，有的优先自己的目录，有的还读 .claude/skills/。以目标客户端文档为准。
  • 用户显式调用语法。 /skills、/<skill-name>、$skill-name 都可能出现。
  • frontmatter 处理。 有的激活后把整份文件交给模型（含 frontmatter），有的剥离 frontmatter 只留正文。
  • 工具可靠性。 来源快速入门提醒，不同模型遵循指令、执行命令的稳定性不同，必要时切换模型。[规范]
  • 实验字段。 allowed-tools 的支持程度因实现而异。

[本课程观点] 提高兼容性的做法：只用必选字段承担关键语义；把环境要求写进 compatibility；不依赖某个客户端特有的路径或 UI；脚本只使用常见运行时与标准库。

[本课程观点] 兼容性不是“一次写好，到处运行”，而是“知道哪些差异可以接受”。如果技能只在团队的一个客户端里使用，可以针对该客户端优化；如果要共享给外部用户，就要避开客户端特有路径、UI 和实验字段，把环境要求写进 compatibility。最容易被忽略的是 frontmatter 处理：有的客户端把整份文件交给模型，有的剥离 frontmatter。不要把关键指令只写在 frontmatter 里，正文必须自足。

提交前预检清单

  • 目录名 = name，字符集与长度合法。
  • description 非空、≤1024 字符，包含“做什么”和“何时用”。
  • YAML 无 Tab、无未加引号的多余冒号、块标量缩进一致。
  • 正文引用的每个文件都存在，路径相对技能根目录且大小写一致。
  • 脚本可执行、不等待输入、失败返回非零退出码。
  • skills-ref validate 与本地脚本均通过。
  • 在至少一个真实客户端中能看到技能并被激活一次。

[本课程观点] 预检清单的作用不是增加流程，而是把“我记得检查”变成“每次都检查”。建议把它接进 CI：格式校验、引用文件存在性、脚本 --help 与失败路径、示例数据上的期望输出，都可以自动跑。人工只保留两类检查：目标客户端里的实际激活，以及输出是否符合业务预期。自动化的部分越稳定，人工评审就越能聚焦在判断上，而不是重复发现同一个格式错误。

[本课程观点] 把这一节的每条要求对应到一个失败场景：如果不这样做，会出现什么可观察的错误？写不出错误的条目，要么删掉，要么补上具体字段、阈值或命令。

如果你只记住三件事

  1. 规范是严格的，客户端可能宽松；提交前用校验工具，而不是靠“能加载”。
  2. 最高频的失败是 name 与目录不一致、描述为空、YAML 冒号/缩进错误。
  3. 跨客户端复用要避开客户端特有路径、UI 与实验字段，关键要求写进 compatibility。

练习

基础

[本课程观点] 运行 node tools/validate-skills.js examples，记录 SUMMARY 行。然后复制一个示例目录，故意把 name 改成大写，再运行一次，观察输出差异。

提示与自检

[本课程观点] 应看到 FAIL 与具体原因（如 name 不匹配目录或含非法字符），且 SUMMARY 的 failed 增加。完成后删除副本，避免污染 examples。

基础

[本课程观点] 回到本页第一个概念小节，用两三句话说明它解决什么问题，并举一个你工作中会遇到的例子。

提示与自检

[本课程观点] 合格答案要包含“问题—做法—具体场景”三部分；只复述小节标题，或举一个与本页无关的例子，都不算完成。

进阶

[本课程观点] 给出一条命令，统计某个 SKILL.md 中 description 的字符数（不依赖校验脚本）。再说明为什么“字符数”和“token 数”不是一回事。

提示与自检

[本课程观点] 可用 awk/sed 截取描述段落再 wc -m，或直接看你所用编辑器。字符数对应规范上限 1024；token 数取决于分词器，且中文与英文比例不同。规范限制的是字符数。

进阶

[本课程观点] 把本页的方法用到你自己的一个真实任务上，写出两条可执行指令和一个别人能照着做的验证方式。

提示与自检

[本课程观点] 两条指令要具体到字段、命令、阈值或判断标准；验证方式必须给出可观察的结果，例如某个文件存在、某条命令退出码为 0、某个字段等于期望值。

挑战

[本课程观点] 构造一个“能通过宽松客户端加载、但违反规范”的 SKILL.md，列出它违反的条款，并说明它在哪些场景下会真正出问题（而不是仅仅不优雅）。

评分点
  • 完整回应题目中的两个关键要求：2 分
  • 给出可验证的检查、示例或对照：2 分
  • 说明一个取舍、边界或失败情况：1 分
