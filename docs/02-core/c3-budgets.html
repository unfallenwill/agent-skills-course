S2 读懂规范

渐进披露的工程实现：预算、拆分与加载触发

把“渐进披露”落到工程细节：每层多少 token、SKILL.md 的 500 行与 5000 token 预算、如何拆分并写出明确的加载触发。

阶段：S2 读懂规范 · 建议 35 分钟 · 先修：Frontmatter 字段

[本课程观点] “保持精简”是句正确的废话。工程上需要具体阈值、可执行的拆分方法和可验证的加载条件（load condition）。这一页给出三样东西：预算、拆分依据、加载触发的写法。

三层预算

层级预算来源与性质超支后果
元数据每技能约 50–100 token（规范写作约 100）[规范] 规范与客户端实现指南技能一多，目录本身占满启动上下文
指令（SKILL.md 正文）少于 5000 token；主文件少于 500 行[规范] 规范“建议”，非硬性校验激活成本高，注意力被稀释，指令互相干扰
资源单个文件尽量聚焦，按需读取[规范] 规范一次读入过多，等于把正文预算又花了一遍

注意“建议”二字：500 行、5000 token 不是校验器会拒绝的硬门槛，而是设计基准。超过并不自动失败，但你需要一个明确理由，并确认没有更好的拆分方式。来源的建议原文是“保持主 SKILL.md 在 500 行以下；把详细参考资料移到独立文件”。[规范]（specification.md）

[规范] 预算是“设计基准”，不是“发布条件”。超过 500 行不一定会被拒绝，但你应该能解释为什么不能拆：是因为这些内容每次都必须一起读，还是因为拆分后模型会漏读？前者可以保留，并在正文开头说明原因；后者说明拆分方式不对，应该按加载条件重新分。另一个常见超支来源是示例：同一个流程放了五段不同风格的输出示例，实际只需一个最有代表性的。删示例往往比删规则更安全，也更有效。

[本课程观点] 把这一节的每条要求对应到一个失败场景：如果不这样做，会出现什么可观察的错误？写不出错误的条目，要么删掉，要么补上具体字段、阈值或命令。

先测量，再讨论

[本课程观点] 不要凭感觉判断“长不长”。用三个命令建立基线：

# 行数
wc -l SKILL.md

# 字符数（中文按字符计，比字节数更接近真实体量）
wc -m SKILL.md

# 字节数，用于确认编码与文件大小
wc -c SKILL.md

[本课程观点] Windows PowerShell 可用 (Get-Content SKILL.md).Count 统计行数，(Get-Content SKILL.md -Raw).Length 统计字符数。Git Bash 下 wc 可直接使用。

token 数没有通用精确命令，因为不同模型分词器不同。可以用所选模型提供商的计数工具，或按经验粗估：中文约每字 1–2 token，英文约每 4 字符 1 token，代码与符号通常更费。[本课程观点] 估算是为了发现数量级问题（是 4000 还是 12000），不是为了精确计费。

一个实用门槛

[本课程观点] 如果 wc -l 显示超过 500 行，先不要争辩“内容都重要”。强制自己做一次分类：每次执行都要用的、只在特定分支用的、几乎从不用的。后两类都应移出主文件。教程 2 会用一个 180 行的例子完整走一遍。

[本课程观点] 测量时要区分“文件体量”和“激活成本”。SKILL.md 的行数与字符数能反映激活时读入的文本量；支持文件只有在被加载时才计入。因此，一个 200 行的主文件加三个 100 行的参考文件，激活成本可能远低于一个 500 行的主文件。测量顺序应该是：先看主文件，再看哪些参考文件会在常见路径上被读取。只统计整个目录的大小，会高估或低估真实成本。

按“触发条件”拆，而不是按长度切

[规范] 最常见的错误是把长文按行数平均切成三份，分别命名为 part1.md、part2.md、part3.md。这没有降低认知负担，只是把“读一篇长文”变成“猜该读哪一篇”。

[规范] 正确的拆分依据是加载条件。同一份内容，只有在相同情境下才会一起被需要，才应该放在同一个文件里。三种可用的切法：

  1. 按任务分支切。 主流程每次都要；只在“遇到扫描件”时才需要 OCR 细节。→ references/ocr.md
  2. 按阶段切。 填写前需要字段字典；填写后需要校验规则。→ references/fields.md 与 references/validation.md
  3. 按数据域切。 法务条款、财务口径、技术规格各自独立。→ references/legal.md、finance.md、technical.md

规范对 references/ 的建议也是“单个文件保持聚焦”，因为 Agent 按需加载，文件越小越省。[规范]（specification.md）

[规范] 按触发条件拆分还有一个好处：它让“什么时候该读什么”变成可以评审的设计，而不是作者的个人习惯。评审者可以问：这个文件在什么情况下被读？如果条件永远不成立，它就是死文件；如果条件几乎总是成立，它就应该并回主文件。拆分不是目的，减少每次激活的无关内容才是。每次拆完都问一遍这个问题，结构会越来越稳。

加载触发：写成可判断的条件

拆分后，主文件必须告诉 Agent 什么时候去读哪个文件。来源给出的对比例子很直接：“Read references/api-errors.md if the API returns a non-200 status code” 比泛泛的 “see references/ for details” 有用得多。[规范]（best-practices.md）

[本课程观点] 一个好触发包含三部分：

当 [可观察的条件] 时，读 [具体文件路径]，用于 [要解决的问题]。
差好区别
详见 references/。当 API 返回非 200 时，读 references/api-errors.md，按状态码查重试策略。条件可观察、路径具体、目的明确
需要时查看字段说明。当要填写或校验字段值时，先读 references/fields.md；遇到未知字段名必须停下来查表。把“需要”落成具体动作
更多内容见 assets。生成最终报告前，套用 assets/report-template.md，不要自行发明章节。说明“何时”与“为什么”

[规范] 触发条件最好用执行中能直接观察到的信号：状态码、文件扩展名、缺失字段、命令退出码。避免用“如果复杂”“如果需要更多信息”这类模型无法稳定判断的措辞。

[规范] 触发条件最好写在流程的对应步骤里，而不是集中放在文末。模型执行到那一步时，正好看到“如果出现 X，读 Y”，比先读完整篇流程再回头找参考更可靠。条件要尽量使用执行中能直接观察的信号：命令退出码、文件扩展名、字段是否缺失、API 状态码。避免“如果需要更多信息”这种只能靠主观判断的措辞，因为它等于没有条件。

[规范] 还要避免触发条件互相重叠。两个文件都写“遇到错误时读”，模型就要猜该读哪个；更好的做法是按错误类型分工，例如“校验失败读 errors.md，网络失败读 retry.md”。如果确实无法细分，就合并成一个文件，而不是让模型做无依据的选择。清晰的边界比更多的文件更有价值。

一个拆分前后对比

[本课程观点] 假设一个 PDF 表单技能的 SKILL.md 有 640 行，结构如下：

## 流程                 40 行
## 字段说明            310 行
## 常见错误码          120 行
## 三个完整示例        150 行
## 许可证与致谢         20 行

[本课程观点] 拆分后：

pdf-form-filler/
├── SKILL.md                      # 约 110 行
├── references/
│   ├── fields.md                 # 字段说明
│   ├── error-codes.md            # 错误码与处理
│   └── examples.md               # 完整示例
└── assets/
    └── report-template.md

[本课程观点] 主文件保留：前置检查、五步流程、默认决策、三个 Gotchas、验证命令，以及三句加载触发。字段说明、错误码、示例分别按条件加载。

[本课程观点] 注意：不是所有内容都值得保留。那 20 行“许可证与致谢”应该放进 license 字段或仓库 LICENSE，而不是占正文；150 行示例里如果有三个几乎相同的例子，保留一个最有代表性的即可。拆分的第一步往往是删除。

[本课程观点] 这个例子真正减少的不是行数，而是“每次激活都要处理的分支”。字段说明、错误码和完整示例都只在特定步骤需要，移到资源层后，常规路径只读 110 行。注意主文件仍然保留了分类默认、Gotchas 和验证命令，这些是每次执行都要用的判断依据。拆分时最容易犯的错，是把“判断规则”也一起移走，结果模型在需要做决定时手上没有依据，只能回头读参考，步骤反而变多。

引用深度与命名

  • 只深一层。 所有 references 都从 SKILL.md 直接引用，避免 a → b → c 的链条。
  • 文件名表达内容。 fields.md 比 doc2.md 好；模型看到文件名就能判断相关性。
  • 不要用中文文件名以外的特殊字符。 空格、括号、# 在不同 shell 与 URL 编码下容易出问题；用短横线分隔。
  • 路径大小写一致。 Windows 不区分大小写，Linux 区分；在 CI 或云端运行时可能突然失败。

[本课程观点] 命名和深度看似是小事，实际影响模型的选择成本。文件名越能表达内容，模型越容易判断“这个文件与当前问题相关”；路径越浅，解析和读取越稳定。跨平台时还要注意大小写：Windows 不区分，Linux 区分，同一份技能在本地能跑、在 CI 里却找不到文件，往往就是这个原因。把路径当作接口的一部分来设计，而不是随手起名。

[本课程观点] 把这一节放回真实任务检验：找一个会用到它的决定，写出遵守与不遵守两种做法，并指出不遵守时会出现什么可观察的错误。写不出具体错误，说明还需要更具体的场景、字段或命令。

如果你只记住三件事

  1. 预算是每技能元数据约 50–100 token、正文少于 5000 token / 500 行、资源按需。
  2. 拆分依据是“是否在同一情境下被需要”，不是行数或章节长度。
  3. 每个支持文件都要有可观察的加载触发：条件、路径、目的，三者缺一不可。

练习

基础

[本课程观点] 写出统计 SKILL.md 行数与字符数的两条命令，并说明为什么不能只看字节数。

提示与自检

[本课程观点] wc -l SKILL.md 与 wc -m SKILL.md。字节数会因 UTF-8 中文编码而虚高（一个汉字通常 3 字节），不能直接对应模型看到的 token 体量。

基础

[本课程观点] 回到本页第一个概念小节，用两三句话说明它解决什么问题，并举一个你工作中会遇到的例子。

提示与自检

[本课程观点] 合格答案要包含“问题—做法—具体场景”三部分；只复述小节标题，或举一个与本页无关的例子，都不算完成。

进阶

[本课程观点] 把“详见 references/errors.md”改写成一条合格的加载触发，场景是批量导入失败。

提示与自检

[本课程观点] 示例：“当导入命令以非零退出码结束，或输出中出现 row_error 时，读 references/errors.md，按错误码决定跳过、修正还是终止整批导入。”检查是否包含条件、路径、目的。

进阶

[本课程观点] 把本页的方法用到你自己的一个真实任务上，写出两条可执行指令和一个别人能照着做的验证方式。

提示与自检

[本课程观点] 两条指令要具体到字段、命令、阈值或判断标准；验证方式必须给出可观察的结果，例如某个文件存在、某条命令退出码为 0、某个字段等于期望值。

挑战

[本课程观点] 你有一个 520 行的 SKILL.md，内容为：流程 60 行、SQL 方言差异 180 行、输出模板 40 行、12 个查询示例 200 行、变更日志 40 行。给出拆分与删除方案，并说明每一部分为什么留下或移走。

评分点
  • 完整回应题目中的两个关键要求：2 分
  • 给出可验证的检查、示例或对照：2 分
  • 说明一个取舍、边界或失败情况：1 分
