S5 交付与迁移

案例 2：团队代码评审（代码工作流）

用 Skill 固化团队的评审关注点与输出格式，同时避免变成噪声制造机。重点在控制校准与历史 PR 验证。

阶段：S5 交付与迁移 · 建议 45 分钟 · 先修：S3、S4 完成

代码评审技能最容易变成“什么都提一句”的噪声机器。这个案例的重点是控制：只报能指出后果的问题，按风险排序，把风格偏好降级，并用历史 PR 检验召回与误报。

情境

一个 12 人的后端团队，每周约 40 个 PR。过去半年发生三次生产事故：一次 SQL 注入、一次越权访问、一次并发扣款重复。复盘发现，三次问题在评审中都有人“隐约觉得不对”，但没有人明确指出触发条件与后果；评审意见更多集中在命名和格式上。

团队已经启用了 linter、类型检查与 SAST（静态应用安全测试），但工具无法判断业务层面的授权边界与幂等性。他们希望用 Skill 把资深工程师的评审关注点固化下来，同时明确：不要重复工具能发现的问题，不要制造噪声。

需求

类型要求可验证标准
覆盖优先检查授权、注入、并发、数据丢失、错误泄露在 10 个历史 PR 上，已知问题被检出 ≥7 个
精确每条发现必须能指出具体行与失败场景随机抽 10 条发现，≥8 条能被资深工程师认可
分级Blocker / Major / Minor / Nit，Nit 不超过 3 条输出结构符合模板；Blocker 有触发条件
范围只评审本次 diff 及直接影响不出现“建议重构整个模块”这类无边界意见
效率不重复 linter/typecheck 已覆盖的问题输出中无纯格式/类型错误

设计与权衡

被否决的方案

  1. 把 200 条规则的完整规范塞进 SKILL.md。 正文过长，模型抓不住重点；规则之间冲突时无法判断优先级。否决理由：上下文成本高、可执行性差。
  2. 替代 linter，做全量静态检查。 模型不适合稳定执行机械规则，且会与现有 CI 重复。否决理由：不可靠、浪费。
  3. 要求 Agent 阅读整个仓库后再评审。 成本高、范围失控，容易对未改动代码发表意见。否决理由：偏离 diff 范围。
  4. 只给一份“最佳实践”清单。 得到的是通用建议，无法发现本项目的授权边界与幂等约定。否决理由：缺少真实专长。
  5. 把所有发现都标为 Blocker，确保不漏。 噪声导致团队忽略评审；失去分级意义。否决理由：精确率崩塌。

采用的结构

  • 风险优先的自由式检查：给关注点与判断标准，不规定逐行扫描顺序，适应不同代码结构。
  • 严格的范围与分级：只评审 diff；Blocker 必须能说出触发条件与后果。
  • 输出模板：位置、问题、证据、影响、建议五段式，强制可行动。
  • Gotchas：行号来自新文件、跳过生成文件、测试密钥的级别、不重复工具发现。

这是“分段校准”的典型：检查维度给自由，报告格式与分级给规定。来源建议按任务脆弱性匹配控制强度；评审路径因代码而异，但严重级别与输出结构必须一致。[源站]（best-practices.md）

取舍

决定代价为什么接受
不覆盖全部规则可能漏掉低频问题聚焦高损失类别；其余交给工具与人工
Nit 限 3 条部分风格问题不提保护信噪比；风格交给 formatter
要求失败场景部分“感觉不对”的问题无法报告无法说明后果的意见不可行动
不读整个仓库跨模块影响可能漏看通过“相关上下文”按需读取，而不是全量
保留人工评审仍需资深工程师投入技能做第一遍筛查，不替代判断

三项关键取舍：决定、被否决的替代方案与理由

决定被否决的替代方案为什么
按风险维度自由检查把 200 条规则清单塞进正文规则过长会稀释重点；判断维度能让模型按代码结构调整顺序
Blocker 必须能说出失败场景所有发现都标 Blocker 以确保不漏噪声会让团队忽略评审；分级必须以可复现后果为依据
用历史 PR 验证召回与误报只用虚构样例验收历史 PR 含真实缺陷与项目约定，能同时测召回和误报

第一个取舍把“检查顺序”交给模型，把“检查维度”留给作者。代价是不同 PR 的评审路径不一致；收益是模型能根据代码结构选择重点，而不是机械执行一份长清单。评审质量取决于维度是否覆盖高风险类别，而不是规则条数。

第二个取舍直接牺牲“零漏报”的错觉。把一切标成 Blocker 看似安全，实际会让团队失去分级信号；要求每条 Blocker 给出触发条件与后果，才能让严重级别可复核。少数无法说明后果的问题，降级为 Major 或放入“待确认”。

第三个取舍把验证建立在历史数据上。虚构样例往往过于干净，无法暴露权限边界、幂等和错误泄露；历史 PR 有真实上下文，也能测出误报。代价是需要人工标注种子问题，但这是获得可信召回率的必要成本。

## 何时使用 / 不适用

当用户要求评审 PR、diff 或合并前检查时使用。不适用于生成完整重构方案、替代 linter/typecheck，或评审未改动的历史代码。

## 参考文件

当需要判定严重级别，或 Blocker 与 Major 的边界不清时，读 `references/severity-guide.md`，按其中的触发条件与示例定级。

# Code Review

## 范围

只评审本次变更及其直接影响。不要重写整个仓库，不要评论未改动的历史代码，除非变更使其变得不安全。

## 流程

1. 读取 diff 与相关上下文（调用方、schema、配置）。
2. 按风险从高到低检查：
   - 认证与授权：每个新入口是否校验身份与权限？
   - 注入：SQL、命令、模板、路径拼接是否使用参数化/转义？
   - 并发：共享状态、锁、幂等性、竞态。
   - 数据丢失：删除、覆盖、迁移是否可回滚？
   - 错误泄露：错误信息是否暴露内部路径、SQL、堆栈或 PII？
3. 对照仓库约定（命名、分层、错误处理）检查一致性。
4. 只报告能指向具体行、并能说明后果的问题。
5. 按模板输出，按严重级别排序。

## 严重级别

- **Blocker**：会导致安全漏洞、数据丢失或生产故障，合并前必须修复。
- **Major**：在常见条件下会产生错误行为，应有明确修复计划。
- **Minor**：可维护性、可读性、边界防御；不阻塞合并。
- **Nit**：风格偏好；最多 3 条，且必须标注为可选。

## 输出模板

```markdown
## 结论
<Blocker 数量> 个阻塞项，<Major 数量> 个主要问题。

## 发现
### [Blocker] <标题>
- 位置：<file>:<line>
- 问题：<一句话说明缺陷>
- 证据：<引用 diff 中的代码或调用链>
- 影响：<具体失败场景>
- 建议：<最小修复方向>

## 未覆盖
- <未检查的部分及原因>
```

## Gotchas

- 行号必须来自本次 diff 的新文件行号；不要引用旧版本行号。
- 生成文件、锁文件、快照测试默认跳过；在“未覆盖”中说明。
- 测试代码中的硬编码密钥也应报告，但级别通常为 Major，不是 Blocker。
- 不要因为“可能有问题”就报 Blocker；必须能说出触发条件与后果。
- 仓库已有 lint/typecheck 能发现的问题不要重复报告，除非它同时是安全或数据问题。

## 自检

- [ ] 每条发现都有文件与行号
- [ ] 每条都有可复现的失败场景
- [ ] 没有把风格偏好写成 Blocker
- [ ] 明确列出未覆盖范围

验证方法

  1. 历史 PR 集。 选 10 个已合并的 PR，其中 5 个事后确认有缺陷（注入、越权、竞态、数据覆盖、错误泄露各一），5 个无已知问题。标注“应发现的问题”作为种子。
  2. 召回率。 运行技能，统计检出的种子问题数 / 种子总数。目标 ≥70%。
  3. 误报率。 对无问题 PR 的发现逐条人工判定；目标：每条发现至少 80% 被认可为“值得提出”。
  4. 分级一致性。 两位工程师独立给发现分级，计算一致率；Blocker 的分歧必须复盘。
  5. 噪声检查。 统计 Nit 数量、纯格式意见数量、对未改动代码的意见数量；任何一项超阈值都算失败。
  6. 对照。 同一批 PR 跑一次“无技能”基线，比较召回与误报，确认技能确实带来增量而不是复述常识。
CHECKPOINT

合格标准示例：种子召回 ≥7/10；无问题 PR 上平均发现 ≤3 条且 ≥80% 被认可；Nit ≤3；无纯格式意见；每条 Blocker 都写明触发条件与后果。

常见失败模式

失败表现根因预防
Nit 洪水20 条命名/格式意见淹没 2 条安全问题没有数量上限与优先级排序Nit 限 3 条；按严重级别排序
幻觉行号发现指向不存在的行或旧版本行号未约束行号来源要求行号来自本次 diff；自检项
评审生成文件对 lock 文件、快照、生成代码提意见未声明跳过范围Gotcha + “未覆盖”小节
忽略项目约定建议引入团队未使用的框架只依赖通用最佳实践先读仓库约定；把项目规则写进技能
一切皆 Blocker失去分级意义用“可能”代替触发条件Blocker 必须能说出具体失败场景
重复工具发现报告类型错误、格式问题技能范围未与 CI 划界明确“工具已覆盖的不报”
越界重构建议要求重写整个模块缺少 diff 范围约束只评审变更及直接影响

可迁移的经验

  • 评审类技能的价值由“精确率 × 召回率”决定，不是由“提了多少条”决定。
  • 给判断维度自由，给输出结构与分级规定；两者分开校准。
  • 用历史数据做验证，比用虚构样例更可信。
  • 把“无法说明后果”的问题排除在 Blocker 之外，是控制噪声最有效的一条规则。

验证评审技能时，召回和误报要一起看。只测“发现了多少已知问题”，会鼓励模型多报；只测“意见是否被认可”，又会忽略漏报。历史 PR 的价值在于同时提供正例与负例：有缺陷的 PR 用来测召回，无缺陷的 PR 用来测噪声。两者都达标，才能说明技能在真实评审中有用。

还要单独检查“范围”和“分级”。每条发现是否落在本次 diff 内，Blocker 是否能说出触发条件与后果，Nit 是否超过上限。这些检查可以脚本化，也可以人工抽样。把范围与分级做成硬门禁，比继续增加检查规则更能提升信噪比。

练习

基础

给“测试文件里硬编码了一个测试密钥”定级，并说明理由。它应该是 Blocker 吗？

提示与自检

通常 Major，不是 Blocker：真实生产凭证才是 Blocker；测试密钥的影响范围有限，但仍应移除并轮换。若该密钥能访问真实环境，则升级为 Blocker。关键在于影响范围，而不是“密钥”这个词。

基础

回到本页第一个概念小节，用两三句话说明它解决什么问题，并举一个你工作中会遇到的例子。

提示与自检

合格答案要包含“问题—做法—具体场景”三部分；只复述小节标题，或举一个与本页无关的例子，都不算完成。

进阶

设计一条断言，用于检查“没有对未改动代码发表意见”。它能否被自动验证？需要什么输入？

提示与自检

需要 diff 的新增/修改行集合；断言为“每条发现的 file:line 都落在该集合内”。可脚本化：解析输出位置并与 diff 行号比对。人工评审可作为补充。

进阶

把本页的方法用到你自己的一个真实任务上，写出两条可执行指令和一个别人能照着做的验证方式。

提示与自检

两条指令要具体到字段、命令、阈值或判断标准；验证方式必须给出可观察的结果，例如某个文件存在、某条命令退出码为 0、某个字段等于期望值。

挑战

把该技能扩展到“前端 PR”，需要改哪些部分？哪些规则应保留，哪些应替换？给出修改后的关注点列表与两条新 Gotchas。

评分点
  • 完整回应题目中的两个关键要求：2 分
  • 给出可验证的检查、示例或对照：2 分
  • 说明一个取舍、边界或失败情况：1 分
