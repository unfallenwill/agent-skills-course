S5 交付与迁移

案例 1：PDF 表单批量填写（文档处理）

300 份表单、字段名不统一、填错代价高。完整走一遍情境、需求、被否决的方案、SKILL.md、验证方法与失败模式。

阶段：S5 交付与迁移 · 建议 45 分钟 · 先修：S3、S4 完成

这是一类高风险、低容错的文档任务：字段名对不上就整份作废，填错日期或金额会引发合规问题。案例重点不是“怎么用 PDF 库”，而是如何把校验前置，让 Agent 在想清楚之前不要动手。

情境

一家共享服务中心每月要处理约 300 份 PDF 申请表，涵盖入职、报销与供应商登记。表单模板由不同部门维护，字段命名不统一：同样的“申请日期”，有的叫 apply_date，有的叫 ApplicationDate，还有的是带页码后缀的重复字段。业务方提供一份 Excel 值表，列名与表单字段并不一一对应。

过去由两名同事手工填写，平均每份 4 分钟，错误主要出现在：字段串行、日期格式、必填项遗漏、复选框值写错。一次批量返工约半天。团队希望 Agent 承担重复劳动，但明确要求：宁可停下来问，也不要静默填错。

需求

类型要求可验证标准
功能从值表与 PDF 提取字段，建立映射，批量填写给定 3 份样例与值表，输出字段数与预期一致
正确性字段名必须精确匹配；未知字段、缺失必填项必须停止注入一个未知字段，进程以非零码停止并列出可用字段
可追溯每份输出附填写报告：总数、已填、未填、校验结果报告字段齐全，数字可与 PDF 复核
安全不覆盖原文件；不自动压平；不处理加密/扫描件原文件哈希不变；扫描件被拒绝并说明原因
可维护字段类型规则独立于流程；新增模板不改主流程新增一种字段类型只需改 reference

设计与权衡

被否决的方案

  1. 一次性大提示词，把字段表直接贴进正文。 字段表 300 多行，模板一更新就过期；每次激活都付出全部 token；模型容易在长表中错位。否决理由：不可维护、上下文成本高。
  2. 对扫描件先 OCR 再填写。 扫描件没有表单字段，OCR 只能得到文本位置，无法可靠对应字段；错填的置信度反而更高。否决理由：不可验证，风险不可接受。
  3. 用 UI 自动化模拟人工点击。 依赖阅读器版本、窗口尺寸与字体；Agent 环境未必有图形界面。否决理由：脆弱且不可移植。
  4. 让 Agent 直接写一个临时脚本，每次现生成。 首次可能成功，但每次逻辑不同，无法积累修复，也无法做回归验证。否决理由：不可重复。

采用的结构

核心是计划—校验—执行：先提取事实源（form_fields.json），再生成计划（field_values.json），用校验脚本对照两者，只有通过才写文件。这与来源推荐的高风险操作模式一致。[源站]（best-practices.md）

  • 脚本承担确定性逻辑：解析、校验、填写、复核。Agent 不直接操作 PDF 字节。
  • 主文件只写流程与停止条件：约 70 行，每次执行都要用。
  • 字段类型细节进 references：只在遇到未知类型、复选框、单选组时加载。
  • 值表模板进 assets：用户提供 CSV 时参照，不在正文里重复列结构。

取舍

决定代价为什么接受
多一步校验每份多一次脚本运行，批量耗时增加一次返工的成本远高于校验；错误不可逆
不自动压平部分阅读器显示效果不一致压平后不可编辑；应由用户明确要求
扫描件直接拒绝覆盖不了历史纸质档案OCR 填写无法可靠验证；宁可人工处理
未知字段必须停批量任务可能中途暂停猜测字段对应关系会产生静默错误
脚本而非纯指令需要维护 Python 依赖字段解析与 PDF 写入需要确定性

三项关键取舍：决定、被否决的替代方案与理由

决定被否决的替代方案为什么
计划—校验—执行直接写 PDF 后检查结果错误不可逆；前置校验能在写文件前停下并给出可用字段
只接受可填写 PDF对扫描件 OCR 后直接填写OCR 无法可靠对应字段；静默错填比明确拒绝更危险
字段名精确匹配，未知即停按列序或相似度猜字段猜错会串行填充且校验仍可能通过，返工成本高

第一个取舍把风险从“事后发现”移到“写文件前”。代价是每份多一次脚本运行，批量耗时增加；收益是错误不会进入最终文档。对于不可逆的对外文件，这个交换几乎总是值得。

第二个取舍主动放弃扫描件市场。OCR 能提取文字，却无法可靠建立“文字—字段”的对应关系；一旦填错，错误看起来和正确结果一样可信。明确拒绝并转人工，比“尽力而为”更负责。

第三个取舍拒绝按列序或相似度猜测。字段名不一致时，正确做法是停下来建立映射并让人确认，而不是让模型选一个“看起来最像”的字段。这会降低自动化率，但保住了可追溯性。

## 何时使用 / 不适用

当用户需要填写一份或多份可填写 PDF 表单，尤其是字段不匹配代价高的批量任务时使用。不适用于扫描件、加密 PDF、签名字段，或需要 OCR 猜测字段的场景；遇到这些情况应停止并说明。

# PDF Form Filler

## 前置检查

1. 确认 PDF 可填写：`python scripts/analyze_form.py input.pdf`。
   - 若字段数为 0：这是扫描件或纯图片 PDF。停止，请用户提供可填写版本；不要用 OCR 猜测后直接盖章。
2. 确认值文件存在且为 UTF-8 编码。
3. 若输出文件已存在，先复制到 `output/backup/<timestamp>/`，不要覆盖。

## 计划—校验—执行

按顺序执行，不得跳过校验：

1. **提取字段**：`python scripts/analyze_form.py input.pdf` → `form_fields.json`
   （字段名、类型、是否必填、所在页）。
2. **建立映射**：创建 `field_values.json`，把每个字段名映射到值。
   - 字段名必须与 `form_fields.json` 完全一致，区分大小写。
   - 不要按位置或顺序猜测字段。
3. **校验**：`python scripts/validate_fields.py form_fields.json field_values.json`
   - 退出码 0 才能继续。
   - 非 0 时读 stderr，修正映射后重跑；最多 3 轮。
4. **填写**：`python scripts/fill_form.py input.pdf field_values.json output.pdf`。
5. **复核**：`python scripts/verify_output.py output.pdf form_fields.json field_values.json`
   - 检查页数未变、已填字段数与预期一致、必填字段无空值。

## 停止条件

出现以下任一情况，停止并报告，不要自行处理：

- PDF 无表单字段或已加密。
- 值文件中有字段名在表单中不存在。
- 必填字段缺少值。
- 校验连续 3 轮失败。
- 输出页数与输入不一致。

## 报告模板

```markdown
## 填写结果
- 输入：<input.pdf>（<n> 页，<m> 个字段）
- 输出：<output.pdf>
- 已填字段：<filled>/<total>
- 未填必填项：<none 或列表>
- 校验：PASS / FAIL（附错误摘要）
- 备注：跳过的项目与原因
```

## Gotchas

- 同名字段可能出现在多页。`analyze_form.py` 会列出页码；映射按“字段名 + 页码”核对，不要只按名字。
- 复选框的值通常是导出值（如 `/Yes`、`/1`），不是 `true`。未知类型先读 `references/field-types.md`。
- 签名字段不能通过程序填写；遇到时报告“需人工签署”，不要生成空白签名框。
- 部分阅读器不显示新填的值，除非压平外观流（flatten）。只有在用户明确要求时才压平，因为压平后不可再编辑。
- 加密 PDF 需要先解密；没有密码时停止，不要尝试破解。

## 参考文件

- 当遇到未知字段类型、复选框/单选组，或值格式报错时，读 `references/field-types.md`，按类型选择值的写法。
- 当用户提供 CSV 值时，参照 `assets/value-template.csv` 的列结构；列名不是字段名时先建立映射表，不要直接按列序填写。

验证方法

  1. 夹具测试。 准备 3 份 PDF：正常双页表单、含重复字段名的表单、无字段的扫描件；各配一份正确值表与一份错误值表。
  2. 正向。 正常表单应输出与输入相同页数、已填字段数等于值表字段数、必填项无空值，校验退出码 0。
  3. 负向。 未知字段应以非零码停止，stderr 列出可用字段；扫描件应被拒绝，且不生成输出文件。
  4. 幂等。 对同一输入运行两次，输出应一致（除时间戳），且原文件哈希不变。
  5. 回归。 每次修改字段类型规则后，重跑全部夹具；记录通过数，而不只是“这次看起来对”。
  6. 人工复核。 随机抽 5 份输出，在阅读器中打开，确认显示值与值表一致；这是断言难以覆盖的部分。
CHECKPOINT

如果你要实现这个技能，至少验证：3 个夹具全部通过；未知字段与扫描件都被拒绝；重复运行不改变原文件；每份输出都有报告且数字可复核。

常见失败模式

失败表现根因预防
字段错位姓名填进地址栏，且校验通过按列序而非字段名映射校验脚本要求字段名存在；禁止按位置
重复字段只填一处同一字段在多页出现，只有第一页有值按名字去重，忽略页码事实源包含页码；复核每页字段
复选框写成 truePDF 显示未勾选或值异常不理解导出值（/Yes、/1）未知类型查 references/field-types.md
扫描件“成功”生成一个没有内容的输出未检查字段数为 0前置检查直接拒绝
静默部分填写报告说完成，实际漏了必填项没有复核步骤verify_output.py 比较必填项数量
覆盖原件原文件被改写输出路径等于输入路径强制不同路径；先备份
改了期望值校验脚本报错后，Agent 改脚本让错误消失验证循环缺少“不得修改期望值”期望值来自事实源，修改需人工确认

可迁移的经验

  • 高风险任务先建立“事实源”，再做计划，再校验，最后执行。
  • 把“不确定”变成停止条件，而不是让模型猜。
  • 校验脚本的错误信息要给出可用选项，模型才能自我纠正。
  • 把低频的类型细节放进 references，主流程保持短小。

这个案例的验证重点不是“能不能填”，而是“错的时候能不能停”。正向夹具只证明流程能跑通；负向夹具才证明系统不会静默产生错误文件。评审时先看未知字段、扫描件、必填缺失三类负向用例，再看正向输出的字段数与页数。把所有失败都变成可观察的拒绝，比提高一次成功率更重要。

还要检查幂等与原件保护。同一输入重复运行，输出应一致，原文件哈希不变；否则一次重试就可能覆盖证据。案例中的“先备份、强制不同输出路径、复核页数”不是形式要求，而是为了让错误可回滚。一个不能回滚的批量填写工具，不值得自动化。

进阶

为“值表列名与字段名不一致”设计一个映射步骤：输入、输出、校验规则各是什么？不要直接按列序对应。

提示与自检
