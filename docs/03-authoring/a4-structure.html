设计方法

S3 写出好内容

结构设计：渐进披露与文件组织

把长内容移到 references/，并明确告诉 Agent 什么时候读哪个文件。比较“泛泛指路”和“带条件的加载触发”。

阶段：S3 写出好内容 · 建议 30 分钟 · 先修：上下文经济

[本课程观点] 拆分不是把文件切小，而是把“什么时候需要什么”写进结构。好的结构让模型在正确的时间读到正确的文件；坏的结构只是把一篇长文变成几个猜谜入口。

预算与目标

来源建议主 SKILL.md 保持在 500 行、约 5000 token 以内，只放每次运行都需要的核心指令；确实需要更多内容时，把详细参考资料移到 references/ 等目录。关键不是“移走”，而是告诉模型什么时候加载每个文件。[源站]（best-practices.md）

[源站] 因此，结构设计包含两个动作：

  1. 切分：按加载条件把内容分组。
  2. 指路：在主文件写明每组的触发条件、路径与用途。

[源站] 只做第一步，等于把复杂度藏起来；两步都做，才是渐进披露。

[源站] 两个动作必须一起做。只切分不指路，模型不知道有哪些文件、各自解决什么问题；只指路不切分，主文件仍然臃肿。切分的依据不是章节长度，而是“是否在同一情境下被需要”。如果一个文件只在错误处理时被读，它就应该和正常流程分开；如果两个文件几乎总是一起读，它们可能本就该合并。每次拆分后，都回到主文件检查：读者能否从流程中看出何时该读哪个文件？

[本课程观点] 把这一节的每条要求对应到一个失败场景：如果不这样做，会出现什么可观察的错误？写不出错误的条目，要么删掉，要么补上具体字段、阈值或命令。

加载触发的三种写法

类型示例适用
现象触发当 API 返回非 200 时，读 references/api-errors.md，按状态码查重试策略。错误处理、异常分支
输入触发当输入文件扩展名为 .xlsx 时，先读 references/excel.md，按其中的转换步骤处理。多格式输入
阶段触发在生成最终报告前，读 assets/report-template.md 并严格套用章节结构。输出格式、模板

[本课程观点] 三种写法都遵循同一句式：当 [可观察条件] 时 → 读 [具体路径] → 用于 [解决什么]。其中“可观察条件”最重要；如果条件只能靠模型主观判断（“如果需要更多信息”），触发就会不稳定。

[本课程观点] 三种写法的共同点是“条件可观察”。现象触发依赖执行结果，输入触发依赖文件特征，阶段触发依赖流程位置。它们都比“如果需要”更可靠，因为模型不需要判断自己是否“需要”，只需检查一个事实。写触发时，最好把条件放在流程的对应步骤，而不是集中放在文末；也不要让两个文件共享同一个模糊条件，否则模型又要做选择。触发写得越像一条 if 语句，行为越稳定。

[本课程观点] 还有一个细节：触发条件要覆盖“没有发生”的情况。例如“当校验通过时继续”并不够，还要写“当校验失败时读 errors.md 并停止”。只写成功路径，模型在失败时没有下一步指令，容易自行发挥。把成功与失败两条分支都写出来，才算完整的流程控制。

坏与好：指路方式

坏好
 
## 参考

更多细节请查看 references/ 目录。

[本课程观点] 模型不知道有哪几个文件、各自解决什么、 什么时候该读。

 
## 参考文件

- references/fields.md：当需要填写或校验字段值时读，
  包含每个字段的类型、必填性与示例。
- references/error-codes.md：当命令以非零退出码结束时读，
  按错误码决定重试、跳过或终止。
- assets/template.md：生成最终报告前读，套用其章节结构。
 
## 处理

1. 读取文件。
2. 参考相关文档处理。
3. 输出结果。
 
## 处理

1. 运行 `python scripts/analyze.py INPUT`，得到字段清单。
2. 对照 references/fields.md 建立字段映射；
   未知字段必须停下来询问，不要猜测。
3. 运行 `python scripts/fill.py` 生成输出。
4. 运行 `python scripts/verify.py OUTPUT`；
   失败则回到第 2 步，最多重试 2 次。

[本课程观点] 右边不仅指了路，还把“什么时候算失败”“失败后回哪一步”“最多几次”写清了。这些信息决定了模型能否自我纠正。

[本课程观点] 左边的“更多细节请查看 references/ 目录”有三个问题：模型不知道目录里有什么，不知道每个文件解决什么问题，也不知道什么时候该读。右边把文件、条件、用途一一列出，模型在执行到对应步骤时可以直接判断。第二组对比更进一步：左边只有“读取、参考、输出”三个动词，没有任何可执行动作；右边把脚本、字段映射、未知字段处理、验证与重试次数都写清了。指路不仅是告诉模型“去哪”，还要告诉它“到了之后做什么”。

[本课程观点] 对比时还要注意“路径基准”。正文里的 references/fields.md 是相对于技能根目录的引用；脚本里的路径则取决于工作目录。右边在流程中直接运行 scripts/analyze.py，但没有说明工作目录，这在真实环境中可能失败。更稳妥的写法是让脚本接受显式路径参数，或在正文中说明“从技能根目录运行”。结构设计不仅是文件摆放，也包括执行约定。

一个可复用的目录布局

my-skill/
├── SKILL.md
├── references/
│   ├── fields.md          # 数据/字段字典
│   ├── rules.md           # 领域规则与例外
│   └── troubleshooting.md # 错误码与恢复
├── scripts/
│   ├── validate.py        # 计划校验
│   └── run.py             # 执行
└── assets/
    ├── template.md        # 输出模板
    └── sample.csv         # 最小可用样例

这个布局不是规范要求，而是一个常见起点。[本课程观点] 判断某个文件该放哪里的问题：

  • 它是指令（告诉模型怎么做）→ 主文件或 references。
  • 它是数据（字段表、映射表、样例）→ references 或 assets。
  • 它是可执行逻辑（重复、易错、需要确定性）→ scripts。
  • 它是输出形状（模板、骨架）→ assets，并在生成前引用。

[本课程观点] 这个布局不是模板，而是一个分类练习。指令放主文件或 references，数据放 references 或 assets，可执行逻辑放 scripts，输出形状放 assets 并在生成前引用。分类之后，还要为每个文件写一句触发；没有触发的文件，要么合并，要么删除。一个常见错误是把“字段字典”放进 assets，因为它看起来像数据；但模型需要“读”它来做判断，所以 references 更合适。assets 更适合被套用、填充或展示的内容，而不是需要理解的规则。

[本课程观点] 用一个你熟悉的真实材料照这一节做一遍：先保留必须的字段与判断，再删掉模型已知的解释，最后补一个别人能执行的验证。完成后让同事只看结构，判断他能否说出何时该读哪个文件。

什么时候不该拆

[本课程观点] 拆分也有成本：多一次读取决策、多一个可能漏读的文件、多一处需要同步维护的内容。以下情况建议不拆：

  • 正文只有 100–200 行，且内容每次都用到。
  • 拆出去的内容与主流程强耦合，缺了就无法执行。
  • 你无法为它写出一个可观察的加载条件。
  • 拆完后主文件仍需大段复述该内容才能工作。

来源的建议是让 references 中的单个文件保持聚焦，因为按需加载时文件越小越省；但这不等于“越小越好”。[源站]（specification.md）判断标准仍是：同一情境下是否总被一起需要。

[本课程观点] 不拆的理由要写下来，而不是凭感觉。常见理由是“每次都用”“拆出去会多一次读取”“无法写出可观察的触发”。如果理由成立，就在主文件保留，并在评审时说明；如果只是因为“懒得改”，那还是应该拆。拆分的成本是导航与漏读，收益是激活时的上下文节省；两者要和真实任务一起权衡，而不是追求文件数量或目录美观。

深度、命名与可发现性

  1. 一层深度：所有引用都从 SKILL.md 直接指向目标，避免 A→B→C。
  2. 名字即说明：error-codes.md 比 ref2.md 更容易被正确选择。
  3. 不要动态生成引用：文件名应在编写时固定，避免模型猜测路径。
  4. 清单式入口：在主文件用一个小节列出所有支持文件及其用途，相当于给模型一张目录卡。

[本课程观点] 这四条规则可以合成一句：让引用“可预测”。文件名可预测，模型就能根据当前问题猜到哪里找；路径可预测，执行环境就不会因为大小写或相对路径失败；入口可预测，模型不用先读一遍目录才知道有什么。最忌讳的是动态生成文件名或让模型猜路径，这会把确定性变成运气。技能里的路径应该像 API 一样稳定，改名要当作破坏性变更处理。

[本课程观点] 把这一节放回真实任务检验：找一个会用到它的决定，写出遵守与不遵守两种做法，并指出不遵守时会出现什么可观察的错误。写不出具体错误，说明还需要更具体的场景、字段或命令。

把触发写进流程，而不是附录

[本课程观点] 许多作者把加载说明塞在文末，模型读到一半就开始执行，根本到不了那里。更稳的做法是把触发嵌进对应步骤：

## 流程

1. 读取输入并列出字段。
2. 建立映射：
   - 字段名在 references/fields.md 中有定义时，按其类型处理。
   - 出现未定义字段时，停止并询问用户；不要自行猜测。
3. 生成输出（assets/template.md）。
4. 运行 `python scripts/verify.py output/` 验证。

[本课程观点] 这样，模型在需要做映射时正好看到加载条件，而不是在 300 行之后才发现“还有一个参考文件”。

[本课程观点] 把触发嵌进流程，本质上是把“参考文件”变成“流程的一部分”。模型不需要记住文末有一份附录，它在做字段映射时自然会看到“未定义字段读 fields.md”。这也让评审更容易：评审者可以沿着流程走一遍，检查每一步是否有足够的输入、明确的动作和可验证的输出。如果某个触发只出现在文末，它很可能在实际执行中被忽略；把它移到对应步骤，或至少在步骤中重复一次。

[本课程观点] 把这一节的每条要求对应到一个失败场景：如果不这样做，会出现什么可观察的错误？写不出错误的条目，要么删掉，要么补上具体字段、阈值或命令。

如果你只记住三件事

  1. 拆分后必须写加载触发；没有触发的 references 等于被遗忘的文件。
  2. 触发要可观察：现象、输入特征或流程阶段，而不是“需要时”。
  3. 引用保持一层深度，文件按“是否总被一起需要”分组，而不是按长度。

练习

基础

[本课程观点] 把“详见 references/errors.md”改成现象触发式写法。

提示与自检

[本课程观点] 示例：“当验证脚本以退出码 4 结束时，读 references/errors.md，找到对应错误码并按其恢复步骤处理。”检查是否包含条件、路径、用途。

基础

[本课程观点] 回到本页第一个概念小节，用两三句话说明它解决什么问题，并举一个你工作中会遇到的例子。

提示与自检

[本课程观点] 合格答案要包含“问题—做法—具体场景”三部分；只复述小节标题，或举一个与本页无关的例子，都不算完成。

进阶

[本课程观点] 一个技能同时处理 CSV、XLSX、JSON 三种输入，各有不同的读取规则。给出 references 拆分方案与三条触发，要求主文件不重复具体规则。

提示与自检

[本课程观点] references/csv.md、excel.md、json.md；触发按扩展名或探测结果：“当扩展名为 .xlsx 时读 excel.md”“当文件首字符为 { 或 [ 时读 json.md”。主文件只保留统一的后续流程与失败处理。

进阶

[本课程观点] 把本页的方法用到你自己的一个真实任务上，写出两条可执行指令和一个别人能照着做的验证方式。

提示与自检

[本课程观点] 两条指令要具体到字段、命令、阈值或判断标准；验证方式必须给出可观察的结果，例如某个文件存在、某条命令退出码为 0、某个字段等于期望值。

挑战

[本课程观点] 评审一个你写过的技能：列出每个支持文件，指出哪些没有明确加载触发、哪些触发不可观察、哪些文件其实应该合并。给出一版修订后的“参考文件”小节。

评分点
  • 完整回应题目中的两个关键要求：2 分
  • 给出可验证的检查、示例或对照：2 分
  • 说明一个取舍、边界或失败情况：1 分
