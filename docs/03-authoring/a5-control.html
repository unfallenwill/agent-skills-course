设计方法

S3 写出好内容

控制校准：自由度与规定性的取舍

同一个 Skill 里，不同部分需要不同强度的控制。学会按“脆弱性”决定是给自由还是给死命令，并提供默认值而非菜单。

阶段：S3 写出好内容 · 建议 30 分钟 · 先修：结构设计

[本课程观点] 同一个 Skill 里，有些部分应该放手让模型判断，有些部分必须一字不差地执行。把“给自由”和“给死命令”搞反，是很多技能失效的根源：该严的地方模糊，该活的地方僵化。

准则：控制强度匹配任务的脆弱程度

来源的表述是：让指令的具体程度匹配任务的脆弱性。当多种做法都有效、任务能容忍变化时，给 Agent 自由；当操作脆弱、一致性很重要或必须遵循特定顺序时，要写得极具规定性。大多数技能是混合体，应逐部分独立校准。[源站]（best-practices.md）

任务特征控制方式写法
多种路径都可行；结果可容忍风格差异给自由描述目标、判断标准与原因，不规定每一步
顺序错了会丢数据；命令参数不能改给规定精确命令、固定顺序、禁止改参数
高风险但路径灵活混合规定检查点与停止条件，过程给自由

[源站] 判断“脆弱性”可以问三个问题：做错了能不能撤销？换一种做法结果是否仍然可接受？多个步骤之间是否有严格顺序？三个答案里有一个是“不可逆”或“必须一致”，就应该偏向规定性。反过来，如果结果可逆、风格差异可接受、顺序不影响正确性，就应该给自由，并把判断标准解释清楚。控制强度不是作者的性格，而是任务属性；同一个技能里，不同步骤完全可以使用不同强度。

[本课程观点] 把这一节放回真实任务检验：找一个会用到它的决定，写出遵守与不遵守两种做法，并指出不遵守时会出现什么可观察的错误。写不出具体错误，说明还需要更具体的场景、字段或命令。

给自由的写法：说明看什么，不规定怎么做

[源站] 来源给出的代码评审例子，描述的是关注点而不是精确步骤：

## Code review process

1. Check all database queries for SQL injection (use parameterized queries)
2. Verify authentication checks on every endpoint
3. Look for race conditions in concurrent code paths
4. Confirm error messages don't leak internal details

[源站] 它没有说“先打开第 1 个文件、再运行某个脚本”，因为评审的路径取决于代码结构。它给的是判断维度，模型可以按实际情况决定顺序与深度。

给自由时，解释“为什么”往往比堆规则更有效：理解了目的的 Agent，能在新情境下做出更好的判断。来源在评估指南中也建议用“做 X，因为 Y 容易导致 Z”这样的理由型指令，而不是“永远做 X、绝不 Y”的僵硬命令。[源站]（evaluating-skills.md）

[源站] 给自由不等于什么都不写。自由式指令仍然要给出检查维度和停止条件：看哪些风险、什么算严重、什么情况必须报告、什么情况可以忽略。代码评审的例子之所以有效，是因为它规定了关注点，而不是规定扫描顺序；模型可以根据代码结构决定先看哪里。如果只写“自由评审”，模型就会退回通用建议，输出一堆与项目无关的正确废话。

给规定的写法：命令、顺序、禁止项

[源站] 数据库迁移是典型的高脆弱任务：

## Database migration

Run exactly this sequence:

```bash
python scripts/migrate.py --verify --backup
```

Do not modify the command or add additional flags.

这里不适合写“选择一个合适的迁移工具并备份”。备份是否真的发生、参数顺序是否正确，直接决定能否回滚。规定性不是不信任模型，而是降低不可逆操作的风险。[源站]（best-practices.md）

判断练习

[源站] 问自己：如果模型换一种做法，结果会“不同但可以接受”，还是“可能不可逆地错”？前者给自由，后者给规定。

[源站] 规定性写法的标志是“命令可复制、顺序不可换、禁止项明确”。数据库迁移的例子给出了完整命令、固定参数和“不要修改”的约束，因为这些细节直接决定备份是否发生、能否回滚。规定性不是对模型能力的否定，而是对不可逆操作的保险。写这类步骤时，最好同时说明“为什么不能改”，让模型在遇到变体时知道该停下来问，而不是自行调整参数。

[本课程观点] 把这一节放回真实任务检验：找一个会用到它的决定，写出遵守与不遵守两种做法，并指出不遵守时会出现什么可观察的错误。写不出具体错误，说明还需要更具体的场景、字段或命令。

提供默认值，而不是菜单

[源站] 当多种工具或方法都可行时，选一个默认，简要提及替代方案，而不是把它们作为平等选项列出来。来源的对比例子：

选项太多清晰默认 + 逃生口
 
你可以使用 pypdf、pdfplumber、
PyMuPDF 或 pdf2image……
 
文本提取用 pdfplumber。

对于需要 OCR 的扫描件，改用
pdf2image + pytesseract。

菜单看似“给模型自由”，实际是把选择成本转嫁给模型，并且常常导致它在多个方案之间反复尝试。默认值加明确例外，既减少探索，又保留了必要的灵活性。[源站]（best-practices.md）

[源站] 菜单式写法的问题不只是“选择多”，而是“没有判断依据”。当四个库并列时，模型只能根据训练数据里的偏好选择，而不是根据当前环境。默认值加逃生口的写法，把选择变成了有条件的决策：默认适用于大多数情况，例外有明确触发条件。写默认值时，最好给出理由或环境依据，例如“项目已安装”“跨平台稳定”“无需额外依赖”，这样模型在例外情况下能判断是否偏离。

[本课程观点] 把这一节放回真实任务检验：找一个会用到它的决定，写出遵守与不遵守两种做法，并指出不遵守时会出现什么可观察的错误。写不出具体错误，说明还需要更具体的场景、字段或命令。

程序优先于声明

[源站] Skill 应该教 Agent 如何 approach 一类问题，而不是为某个具体实例给出答案。来源的对比：

具体答案（只对这次有用）可复用方法
 
把 orders 表按 customer_id
连接 customers，筛选
region = 'EMEA'，对 amount 求和。
 
1. 从 references/schema.yaml 读取 schema，
   找到相关表。
2. 按 _id 外键约定连接表。
3. 把用户请求中的筛选条件写成 WHERE。
4. 按需聚合数值列，输出 markdown 表格。

这不意味着技能不能含具体细节。输出模板、“绝不输出 PII（个人身份信息）”这类约束、针对特定工具的指令都很有价值。关键点是：方法要能泛化，即使个别细节是具体的。[源站]（best-practices.md）

[源站] 程序与声明的区别，可以理解为“方法”与“答案”的区别。具体答案只对某个实例有效，方法则能迁移到同类问题。写技能时，先问：这个任务下次换一份数据、换一个客户、换一个仓库，步骤还成立吗？如果只有具体数字成立，就把数字放进示例或参数，把方法写成步骤。具体细节并非不能写，但应该服务于方法，而不是替代方法。一个只会背答案的技能，遇到稍微不同的输入就会失效。

[本课程观点] 把这一节放回真实任务检验：找一个会用到它的决定，写出遵守与不遵守两种做法，并指出不遵守时会出现什么可观察的错误。写不出具体错误，说明还需要更具体的场景、字段或命令。

在一个文件里混合校准

[本课程观点] 下面是一个混合型技能的片段：

## 生成季度报告

### 取数（规定）
必须运行：
python scripts/fetch.py --quarter Q3 --output data/q3.csv
不要改用其他脚本或手工导出。

### 分析（自由）
找出三个最值得管理层关注的发现。判断标准：
- 金额影响超过 10 万元；
- 或环比变化超过 20%；
- 或涉及新客户/新区域。
不要为了凑数而列出无关发现。

### 排版（规定）
套用 assets/quarterly-template.md，章节顺序不可调整；
金额统一保留一位小数，单位为万元。

### 自检（规定）
运行 python scripts/check_report.py output/report.md。
任何 FAIL 都必须修复后重跑，不得跳过。

[本课程观点] 取数与排版是脆弱环节，给死命令；分析是判断环节，给标准与理由；自检是质量门禁，要求必须通过。这种“分段校准”比整篇都写死或整篇都放开更可靠。

[本课程观点] 这个片段展示了“分段校准”的实际写法。取数与排版是不可逆或需一致的环节，所以给死命令；分析是判断环节，所以给标准与理由；自检是质量门禁，所以要求必须通过。每个段落开头的小标题（规定/自由）不是装饰，而是让读者一眼看出控制强度。写自己的技能时，也可以先用这三个标签给每段分类，再检查分类是否合理。如果一段既没有精确命令，也没有判断标准，它大概率会变成模糊指令。

[本课程观点] 把这一节放回真实任务检验：找一个会用到它的决定，写出遵守与不遵守两种做法，并指出不遵守时会出现什么可观察的错误。写不出具体错误，说明还需要更具体的场景、字段或命令。

坏与好：控制的错配

错配问题修正
对迁移写“选择合适方式备份”该严的地方太松，可能无法回滚精确命令、固定顺序、禁止改参数
对评审写“必须按 A→B→C 顺序检查”该活的地方太死，忽略代码结构差异给关注点与判断标准，不规定顺序
对库选择列四个选项把选择成本丢给模型，导致反复试错一个默认 + 一个明确例外
对输出格式只写“整洁美观”不可验证，模型无法判断达标给模板或一个真实样例

[本课程观点] 四行错配分别对应四种常见后果：该严的地方太松，可能无法回滚；该活的地方太死，会忽略代码结构差异；给菜单会让模型反复试错；只写“整洁美观”则无法判断达标。修正方法不是一律写死或一律放开，而是回到脆弱性判断：不可逆、需一致、顺序敏感的地方给规定；可逆、风格可变、路径多样的地方给标准与自由。每改一处，都问自己“换一种做法是否可接受”，答案会决定控制强度。

[本课程观点] 还有一个容易被忽略的错配：把“输出格式”写成形容词。格式是可以用模板或样例约束的，属于可规定的内容；写成“清晰、专业”只会让模型自由发挥。反过来，把“分析思路”写成固定步骤，又会限制模型发现数据中的异常。控制校准的目标不是让技能看起来严谨，而是让关键行为稳定、非关键行为灵活。

[本课程观点] 把这一节放回真实任务检验：找一个会用到它的决定，写出遵守与不遵守两种做法，并指出不遵守时会出现什么可观察的错误。写不出具体错误，说明还需要更具体的场景、字段或命令。

如果你只记住三件事

  1. 控制强度取决于脆弱性：可逆、可变 → 给自由；不可逆、需一致 → 给规定。
  2. 多方案时给默认值和明确的逃生口，不要给菜单。
  3. 教方法而不是背答案；具体细节可以保留，但方法要能泛化。

练习

基础

[本课程观点] 判断应给自由还是规定：（A）删除生产数据库表；（B）给一段代码写总结；（C）生成对外合同 PDF。

提示与自检

[本课程观点] A 规定（不可逆、高风险）；B 自由（可逆、风格可变）；C 规定（对外文件，格式与措辞一致性重要）。判断依据是“换一种做法是否可接受”。

基础

[本课程观点] 回到本页第一个概念小节，用两三句话说明它解决什么问题，并举一个你工作中会遇到的例子。

提示与自检

[本课程观点] 合格答案要包含“问题—做法—具体场景”三部分；只复述小节标题，或举一个与本页无关的例子，都不算完成。

进阶

[本课程观点] 把“你可以用 Jest、Vitest、Mocha 或 Node 内置测试运行器”改成“默认 + 逃生口”的写法，并说明默认选择的理由。

提示与自检

[本课程观点] 示例：“默认使用 Vitest（项目已有配置，无需额外安装）。仅当项目使用 Jest 既有配置时，沿用 Jest。”默认选择应基于项目事实（已安装、配置、团队习惯），而不是个人偏好。

进阶

[本课程观点] 把本页的方法用到你自己的一个真实任务上，写出两条可执行指令和一个别人能照着做的验证方式。

提示与自检

[本课程观点] 两条指令要具体到字段、命令、阈值或判断标准；验证方式必须给出可观察的结果，例如某个文件存在、某条命令退出码为 0、某个字段等于期望值。

挑战

[本课程观点] 选一个你熟悉的流程，把它分成“规定 / 自由 / 验证”三段，并为每段写出至少一条规则。然后指出：如果全部写成规定，会有什么代价？全部写成自由呢？

评分点
  • 完整回应题目中的两个关键要求：2 分
  • 给出可验证的检查、示例或对照：2 分
  • 说明一个取舍、边界或失败情况：1 分
