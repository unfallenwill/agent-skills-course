预备知识

S1 认知准备

提示词、指令与文件式配置

从聊天里的提示词，到可版本控制、可审查、可按需加载的指令文件。理解 SKILL.md 这种“文件式配置”的价值。

阶段：S1 认知准备 · 建议 25 分钟 · 先修：什么是 Agent

[本课程观点] 你可能已经在聊天里“教”过 Agent 怎么做某件事。问题是，那段对话结束后，教过的东西就散了。这一页解释为什么要把指令从聊天搬进文件，以及 SKILL.md 为什么长成“YAML 元数据 + Markdown 正文”这个样子。

提示词、指令、系统提示词：三个常被混用的词

  • 提示词（prompt）：你这一次发给模型的内容。可以是一句话，也可以是一大段。它天然是临时的。
  • 指令（instructions）：告诉模型“应该怎样做”的内容，通常比单次问题更稳定，可被复用。
  • 系统提示词（system prompt）：由客户端或应用在对话开始前注入的高优先级指令，用来设定角色、边界与输出规范。普通用户通常看不到全部内容。

三者的边界并不严格，不同产品叫法也不同。真正有意义的区分是：这段内容是只服务于当前这一轮，还是要长期、稳定、可审查地服务于一类任务？后者就应该落成文件。[本课程观点]

[本课程观点] 另一个区分维度是“谁负责维护”。提示词由使用者临时写，系统提示词由产品团队维护，指令文件则由领域专家维护。Skill 把维护责任从写代码的人转移给了最懂业务的人，这是它最有价值的地方之一。因此，评价一个技能写得好不好，不能只看语言是否流畅，还要看它是否包含只有领域专家才知道的判断。一个由通用模型生成的技能，往往在这道题上失分。

为什么把指令放进文件

[本课程观点] 把说明写在聊天里，至少有三个问题：下次会话不保留；别人无法复用；改动没有历史记录。文件式配置分别给出对应解法：

需求聊天里的说明文件里的指令
复用每次重新粘贴放在固定目录，客户端自动发现
协作截图、口口相传可以提交到仓库、走代码评审
追溯找不到上次怎么改的版本控制记录每次修改与原因
加载一次性全部进入上下文可按需加载，只读相关部分
测试难以构造稳定用例可以配评估用例、脚本与断言

[本课程观点] 这五点里，最容易被低估的是“加载”。文件不仅是存储方式，也是调度单位：Agent 可以先只读目录，再决定读哪个文件。没有文件边界，就没有渐进披露。

[本课程观点] 文件还有一个常被忽略的好处：它可以被测试。聊天里的说明只能靠人回忆“上次是怎么说的”，文件则可以固定下来，配上评估用例、版本记录和评审意见。你可以比较两个版本在同一批任务上的表现，也可以让同事在不打扰你的情况下复现问题。可测试性直接决定了技能能否持续改进。没有文件，改进只能靠模糊印象；有了文件，改进才有基线。

[本课程观点] 把这一节放回真实任务检验：找一个会用到它的决定，写出遵守与不遵守两种做法，并指出不遵守时会出现什么可观察的错误。写不出具体错误，说明还需要更具体的场景、字段或命令。

为什么是 Markdown 和 YAML

Markdown 是一种轻量标记语言，用 # 表示标题、- 表示列表、反引号表示代码。它的优势是人和模型都容易读写，不需要复杂工具链。[本课程观点]

YAML 是一种人类可读的数据序列化格式，用缩进表示层级，用 键: 值 表示字段。Agent Skills 用 YAML 作为前置元数据（frontmatter）的格式，因为客户端需要机器可读地取出 name 与 description，而不必理解整篇自然语言。[外部: https://yaml.org/spec/1.2.2/] YAML 1.2.2 规范：yaml.org/spec/1.2.2（检索于 2026-11-25）。

[源站] SKILL.md 必须包含 YAML frontmatter，其后是 Markdown 正文。正文没有格式限制，写什么最有助于 Agent 完成任务就写什么。推荐包含：分步指令、输入输出示例、常见边界情况。Agent 在决定激活后会加载整个文件，因此较长的内容应考虑拆分到被引用的文件中。（来源：specification.md）

[本课程观点] 把机器可读与人类可读分开，是一种务实的设计。客户端不需要理解整篇中文，就能从 frontmatter 取出名字和描述；人也不需要读懂 YAML 解析器，就能修改流程。两者的边界应该清晰：凡是被程序用来做发现、路由或权限判断的信息，放 frontmatter；凡是指导模型行动的步骤、示例和边界，放正文。混用会导致两个问题：元数据变得臃肿，正文缺少关键约束。

一个最小例子

---
name: weekly-report
description: 把每周销售 CSV 汇总成固定格式的周报。当用户提到周报、销售汇总或需要按周比较数据时使用。
---

## 流程

1. 读取用户提供的 CSV，确认包含 date、region、amount 三列。
2. 按周聚合 amount，输出 markdown 表格。
3. 与上周对比，标出变化超过 20% 的区域。

## 输出格式

| 周次 | 区域 | 金额 | 环比 |

[本课程观点] 这个文件只有十几行，但已经具备 Skill 的关键要素：机器可读的名字与触发描述、人类可读的流程、明确的输出形状。它没有解释“什么是 CSV”，因为模型知道；它写明了列名和阈值，因为这是模型不知道的项目事实。

[本课程观点] 逐行看这个例子：name 与目录一致，description 同时覆盖“周报”和“销售汇总”两种说法，正文只写了列名、周区间和变化阈值这些项目事实。它没有解释 CSV 是什么，也没有教模型怎么画表格。这个取舍不是偷懒，而是假设模型具备通用能力，把篇幅留给真正会出错的地方。你可以用同样的方法检查自己的技能：把每一句问一遍“模型不知道这个吗”，答“知道”的就删掉。

[本课程观点] 用一个你熟悉的真实材料照这一节做一遍：先保留必须的字段与判断，再删掉模型已知的解释，最后补一个别人能执行的验证。完成后让同事只看结构，判断他能否说出何时该读哪个文件。

Skill 不是“更长的提示词”

[本课程观点] 把 Skill 理解成提示词模板，会带来三个错误做法：

  1. 把所有背景都写进去，因为它“反正也是提示词”。但 Skill 会被反复加载到不同会话，每一句都在消耗预算。
  2. 只写一次，不再维护。文件一旦进入仓库，就会像代码一样过时；规范、字段、下游系统都会变。
  3. 忽视触发描述。提示词是你主动发送的，Skill 却要自己争取被选中；描述写不好，内容再好也不会被加载。

[本课程观点] 更准确的理解是：Skill 是一个有元数据、有加载策略、可捆绑资源的能力包。提示词只是它的正文部分。

[本课程观点] 判断一个文件是不是“更长的提示词”，可以看它有没有加载策略。真正的技能会区分元数据、正文和资源，会告诉 Agent 什么时候读哪个文件，会在描述里写清边界。更长的提示词则把所有内容平铺在一起，默认每次都要全部读入。前者是工程结构，后者是文档堆积。这个区别在技能少的时候不明显，技能一多、任务一复杂，就会变成成本与准确率的差距。

一个够用的心智模型

把 Skill 想成一份“交接文档”

[本课程观点] 你要休假两周，把一项 recurring 工作交给一位很聪明、但完全不了解你们业务的新同事。你会写什么？不会写“Excel 是电子表格软件”；会写“每月 3 号前把 A 表第 D 列的数填进 B 系统，注意 B 系统把 0 当成空值”。Skill 就是这份交接文档的可执行版本。

这个类比也解释了为什么“真实专长”如此重要：交接文档的价值，等于你脑子里那些没写进任何手册的东西。[本课程观点]

[本课程观点] 交接文档的类比还能帮你决定“不写什么”。你不会在交接文档里解释 Excel 怎么用，也不会把所有历史决策都抄一遍；你只会写接手人最可能踩的坑、必须遵守的规则、以及遇到异常时找谁。技能同理：它服务于一个具体任务，不是组织知识的全集。把技能当成一次高质量交接，而不是一本百科，篇幅和重点都会更自然。

[本课程观点] 把这一节放回真实任务检验：找一个会用到它的决定，写出遵守与不遵守两种做法，并指出不遵守时会出现什么可观察的错误。写不出具体错误，说明还需要更具体的场景、字段或命令。

如果你只记住三件事

  1. 提示词服务一次对话，指令文件服务一类任务；后者可复用、可评审、可追溯。
  2. YAML frontmatter 提供机器可读的元数据，Markdown 正文提供人机都可读的流程。
  3. Skill 不是更长的提示词，而是带加载策略和资源的能力包；文件边界本身就是设计工具。

练习

基础

[本课程观点] 判断：把“你是一名资深财务分析师，请严谨”写进 SKILL.md 正文，是不是好做法？为什么？

提示与自检

[本课程观点] 通常不是。它没有提供模型不知道的事实，也不改变具体流程，属于空泛的角色设定。除非它能约束可观察的行为（例如“金额一律保留两位小数并注明币种”），否则应删掉。

基础

[本课程观点] 回到本页第一个概念小节，用两三句话说明它解决什么问题，并举一个你工作中会遇到的例子。

提示与自检

[本课程观点] 合格答案要包含“问题—做法—具体场景”三部分；只复述小节标题，或举一个与本页无关的例子，都不算完成。

进阶

[本课程观点] 把下面这段聊天说明改写成 SKILL.md 的正文草稿（不必写 frontmatter）：
“我们周报要用上周一到周日的数，不是自然周；金额是含税的；如果某个区域没有数据，要写 0 而不是留空；最后按金额降序。”

提示与自检

[本课程观点] 应包含四条可执行规则：周区间定义、金额口径、缺失值处理、排序方式。每条都要具体到可验证。若你加了“请注意数据质量”之类的话，删掉——那不是规则。

进阶

[本课程观点] 把本页的方法用到你自己的一个真实任务上，写出两条可执行指令和一个别人能照着做的验证方式。

提示与自检

[本课程观点] 两条指令要具体到字段、命令、阈值或判断标准；验证方式必须给出可观察的结果，例如某个文件存在、某条命令退出码为 0、某个字段等于期望值。

挑战

[本课程观点] 选一个你熟悉的文件格式（例如团队的周报模板、事故复盘模板），指出其中哪些信息适合放 frontmatter 的 metadata，哪些必须放正文，哪些应该放 assets/。说明判断依据。

评分点
  • 完整回应题目中的两个关键要求：2 分
  • 给出可验证的检查、示例或对照：2 分
  • 说明一个取舍、边界或失败情况：1 分
