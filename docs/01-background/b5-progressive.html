预备知识

S1 认知准备

渐进披露：为什么不能把所有内容一次塞进去

用“目录—章节—附录”的类比建立渐进披露直觉，并看清它在 Agent Skills 中对应哪三层、各自花多少 token。

阶段：S1 认知准备 · 建议 25 分钟 · 先修：上下文窗口与 Token

[本课程观点] 假设你的编辑器里装了 40 个 Skill。如果每个 SKILL.md 平均 3000 token，全部常驻就是 12 万 token——还没开始干活，上下文已经满了。渐进披露（progressive disclosure）就是为了避免这种局面。

问题：技能越多，上下文越不够用

[本课程观点] Agent 的能力扩展有一个天然矛盾：

  • 要让 Agent 在需要时想到某个技能，它必须“知道有这个技能”。
  • 要让 Agent 用得好，它必须读到完整指令。
  • 但完整指令很贵，不能对每个技能、每一轮都读。

[本课程观点] 把所有技能全文常驻，会同时付出费用、延迟与注意力三重代价；只给技能名字不给描述，Agent 又无法判断何时该用。渐进披露的做法是：先给最小可判断的信息，再按需要逐层加深。

[本课程观点] 把数字换成感受：一个技能正文 3000 token，十个就是 3 万；这还没有算系统提示词、工具定义和对话历史。窗口再大，也会被这些固定成本吃掉。更麻烦的是，模型需要在几十段描述里判断“这次该用哪个”，描述越相似，误判越多。渐进披露不是省一点钱的技巧，而是让技能数量增长时系统仍然可用的结构性选择。没有它，技能库越大，Agent 越难找到正确的那一个。

[本课程观点] 把这一节放回真实任务检验：找一个会用到它的决定，写出遵守与不遵守两种做法，并指出不遵守时会出现什么可观察的错误。写不出具体错误，说明还需要更具体的场景、字段或命令。

三层加载

[源站] Agent 通过三个阶段加载技能：发现（Discovery）——启动时只加载每个可用技能的名字和描述，刚好够判断是否可能相关；激活（Activation）——当任务匹配某个技能的描述时，Agent 把完整的 SKILL.md 指令读入上下文；执行（Execution）——Agent 遵循指令，按需执行捆绑代码或加载被引用的文件。

层级加载什么何时加载参考成本
第 1 层：元数据name 与 description会话启动时，对全部技能约 100 token / 技能；客户端实现指南给出约 50–100
第 2 层：指令完整 SKILL.md 正文技能被激活时建议少于 5000 token
第 3 层：资源scripts/、references/、assets/ 中的文件指令引用且任务需要时因文件而异

这张表的数字来自规范与客户端实现指南：规范建议 SKILL.md 正文少于 5000 token、主文件少于 500 行；客户端实现指南把目录层描述为每技能约 50–100 token。[源站]（specification.md、adding-skills-support.md）

[源站] 三层之间的关系不是“越深越详细”，而是“越深越有条件”。元数据回答“要不要考虑这个技能”，正文回答“这类任务的标准做法是什么”，资源回答“当前这个分支的特殊情况怎么处理”。因此，正文不应该包含只在 5% 情况下才需要的细节，资源也不应该承担每次都要执行的步骤。判断内容放在哪一层，先问：如果这次用不上，读它是不是浪费？答案是“是”，就往下放，并写清加载条件。

[本课程观点] 把这一节放回真实任务检验：找一个会用到它的决定，写出遵守与不遵守两种做法，并指出不遵守时会出现什么可观察的错误。写不出具体错误，说明还需要更具体的场景、字段或命令。

类比：图书馆、书与附录

[本课程观点] 可以用三层类比来建立直觉：

  1. 目录卡片（元数据）：每本书一张卡，写着书名和一句话简介。你扫一眼就知道要不要借。卡片很小，所以整个柜子都能放在桌上。
  2. 正文（SKILL.md）：真正开始读这本书。它应该自足，能支撑一次完整操作，但不必包含所有历史考据。
  3. 附录与工具箱（references / scripts / assets）：遇到具体问题时再翻。查表、跑脚本、套模板，都在这一步。

[本课程观点] 类比不能过度延伸：Agent 不是真的“先借书再读”，它每次激活都可能重新读取；也没有人类那样的长期记忆。但这个类比能帮你判断内容该放哪一层：决定“要不要用”的信息放第 1 层，决定“怎么做”的信息放第 2 层，只有做某一步才需要的信息放第 3 层。

[本课程观点] 类比的边界也要说清：图书馆的目录卡片不会自动被“理解”，而技能描述会被模型用来做语义判断；书读完就记住了，技能内容却可能被上下文压缩掉。所以不能把类比推得太远。它真正有用的地方，是帮你形成“先判断、再展开”的直觉，以及在写作时问自己：这段信息是目录卡、正文，还是附录？一旦能稳定回答这个问题，内容分层就不会乱。

渐进披露带来什么

  • 可扩展：装 50 个技能，启动时也只需要读 50 段短描述，而不是 50 篇长文。
  • 更准的激活：描述足够具体时，模型能区分相邻技能，不会把所有任务都交给同一个“万能技能”。
  • 更低的单次成本：只有真正相关的技能才付出正文成本。
  • 更易维护：把易变的细节放进独立文件，修改时不必动主流程。

来源在客户端实现指南中算过一笔账：装了 20 个技能的 Agent，不必在启动时支付 20 套完整指令的成本，只支付实际用到的那些。[源站]（adding-skills-support.md）

[源站] 除了成本，渐进披露还改善“可维护性”。当所有内容堆在一个文件里，修改一个字段说明就要重新检查整篇；拆成资源后，变化被限制在局部，评审也更容易聚焦。它同时降低了技能之间的冲突：两个技能都激活时，只有各自真正需要的部分进入上下文，互相矛盾的规则出现概率更低。这些收益不会立刻显现在一次运行里，但会随着技能数量和团队人数增长而放大。

它不是什么

[本课程观点] 为了避免误解，明确三点：

  1. 不是自动摘要。 渐进披露依赖作者把内容切开并写好加载条件；客户端不会替你判断哪段重要。
  2. 不是检索增强生成（RAG）。 它没有向量库和相似度检索；是否加载由模型读描述后判断，或由用户显式调用。
  3. 不是“文件越多越好”。 拆得太碎会增加导航成本和漏读风险；来源建议文件引用保持在一层深度，避免深链。[源站]（specification.md）

[本课程观点] 还要避免一种反向误区：为了“渐进披露”而把所有内容拆成很多小文件，结果主文件变成一张导航表，模型每做一步都要猜该读哪个文件。拆分的前提是你能够为每个文件写出清晰的加载条件；写不出条件，就不要拆。一个好的经验是：先写一个自足的短正文，等它确实超过预算，再按“同一情境下一起需要”的原则拆出一两个文件。结构应该跟着真实需求长出来，而不是先搭架子。

[本课程观点] 把这一节放回真实任务检验：找一个会用到它的决定，写出遵守与不遵守两种做法，并指出不遵守时会出现什么可观察的错误。写不出具体错误，说明还需要更具体的场景、字段或命令。

对设计的三条直接要求

  1. 把描述当成产品入口来写。 它是唯一常量；写得窄，技能不触发；写得宽，处处误触发。第 4 模块会专门训练。
  2. 正文只放“每次都要”的内容。 一次性才用的字段表、长示例、模板，移到资源层。
  3. 给每个资源写加载触发。 “参见 references/”几乎没有用；要写“当 API 返回非 200 时，读 references/api-errors.md”。

[本课程观点] 这三条要求可以落到具体检查：描述里有没有“当用户……时使用”的句子；正文里有没有一段明显是低频细节的内容；每个支持文件旁边有没有“当 X 时读 Y”的触发。三个检查都不通过，说明你写的可能还是一篇提示词，而不是一个可维护的技能。先修结构，再修措辞；结构错了，措辞再好也只能延缓问题。

[本课程观点] 把这一节的每条要求对应到一个失败场景：如果不这样做，会出现什么可观察的错误？写不出错误的条目，要么删掉，要么补上具体字段、阈值或命令。

[本课程观点] 这三条要求不是一次性的写作检查，而是每次修改技能后都应该重跑的自检：描述是否仍覆盖真实说法、正文是否仍只放高频内容、每个资源是否仍有可观察的加载条件。任何一项退化，都会让渐进披露重新变成“把文件堆在一起”。

如果你只记住三件事

  1. 渐进披露分三层：元数据（全部加载）、指令（激活时加载）、资源（需要时加载）。
  2. 它解决的是“技能数量增长”与“上下文有限”之间的矛盾，不是让内容自动变聪明。
  3. 拆分的质量取决于加载触发写得是否具体；没有触发条件的拆分只是把长文切碎。

练习

基础

[本课程观点] 把下列内容分到三层：① 技能名与一句话描述；② “先用 jq 校验 JSON，再写入”；③ 一份 12 页的 API 错误码表。

提示与自检

[本课程观点] ① 元数据；② SKILL.md 正文（每次执行都要）；③ references（只在遇到错误码时读）。若你把错误码表放进正文，激活成本会无谓增加。

基础

[本课程观点] 回到本页第一个概念小节，用两三句话说明它解决什么问题，并举一个你工作中会遇到的例子。

提示与自检

[本课程观点] 合格答案要包含“问题—做法—具体场景”三部分；只复述小节标题，或举一个与本页无关的例子，都不算完成。

进阶

[本课程观点] 某 SKILL.md 正文 620 行，其中 300 行是“字段字典”。请给出拆分方案，并写出至少两条具体的加载触发。

提示与自检

[本课程观点] 方案应把字段字典移到 references/fields.md，主文件保留流程、默认值与校验命令。触发示例：“当需要填写或校验字段值时，读 references/fields.md”“当遇到未知字段名时，先查 references/fields.md 再报错”。只写“详见 references”不合格。

进阶

[本课程观点] 把本页的方法用到你自己的一个真实任务上，写出两条可执行指令和一个别人能照着做的验证方式。

提示与自检

[本课程观点] 两条指令要具体到字段、命令、阈值或判断标准；验证方式必须给出可观察的结果，例如某个文件存在、某条命令退出码为 0、某个字段等于期望值。

挑战

[本课程观点] 设计一个包含 5 个相邻技能（例如 PDF 读取、PDF 表单填写、PDF 合并、PDF 转图片、OCR）的目录。为每个技能写一句 20–40 字的描述，使它们尽可能不互相误触发。再指出哪两个最容易混淆，以及你如何在描述中划边界。

评分点
  • 完整回应题目中的两个关键要求：2 分
  • 给出可验证的检查、示例或对照：2 分
  • 说明一个取舍、边界或失败情况：1 分
