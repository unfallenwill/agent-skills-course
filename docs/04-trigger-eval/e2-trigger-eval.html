S4 触发与评估

触发评估：用查询集调准 description

构造 20 条真实查询、划分训练/验证集、每条跑 3 次算触发率，按五步循环改进而不是堆关键词。

阶段：S4 触发与评估 · 建议 40 分钟 · 先修：描述字段

[本课程观点] “我觉得这个描述挺清楚的”不是证据。触发准确率可以测：准备一批真实查询，标明该不该触发，每条跑多次，算比例。方法不复杂，难的是构造好查询和避免自欺。

第一步：构造查询集

你需要一组真实用户会输入的话，每条标注 should_trigger 是 true 还是 false。来源建议约 20 条：8–10 条应触发，8–10 条不应触发。[源站]（optimizing-descriptions.md）

[
  {
    "query": "I've got a spreadsheet in ~/data/q4_results.xlsx with revenue in col C and expenses in col D — can you add a profit margin column and highlight anything under 10%?",
    "should_trigger": true
  },
  {
    "query": "whats the quickest way to convert this json file to yaml",
    "should_trigger": false
  }
]

应触发查询：沿四个轴变化

  • 说法：正式、随意、带错别字或缩写。
  • 明确程度：有的直接点名领域（“分析这个 CSV”），有的只描述需求（“老板要我从这个数据文件做张图”）。
  • 细节：短句与带文件路径、列名、背景的长句混合。
  • 复杂度：单步任务与多步工作流混合，测试技能在长链条中是否仍能被识别。

[源站] 最有价值的正例，是“技能会帮上忙、但单看查询不明显”的那些。如果查询已经把技能要做的事说得一清二楚，任何合理描述都会触发，测不出差异。

不应触发查询：优先“近邻”

[源站] 来源强调，最有价值的负例是近邻（near-miss）：与技能共享关键词或概念，但实际需要别的东西。弱负例（“写个斐波那契函数”“今天天气如何”）什么都测不出。

弱负例强负例为什么强
写一个排序算法“帮我改一下 Excel 预算表里的公式”共享“表格/数据”概念，但需要表格编辑，不是 CSV 分析
今天天气怎么样“写个 Python 脚本把 CSV 每行上传到 Postgres”涉及 CSV，但任务是数据库 ETL

让查询更像真的

真实提示里通常有：文件路径（~/Downloads/report_final_v2.xlsx）、个人背景（“我经理让我……”）、具体细节（列名、公司名、数据值）、口语、缩写与偶发错别字。[源站]

第二步：每条跑多次，算触发率

模型行为是非确定性的：同一条查询这次触发、下次可能不触发。来源建议每条跑 3 次作为起点，计算触发率（触发次数 / 运行次数）。应触发的查询，触发率高于阈值（0.5 是合理默认）算通过；不应触发的，低于阈值算通过。[源站]（optimizing-descriptions.md）

[源站] 20 条 × 3 次 = 60 次调用，手动做很痛苦，应该脚本化。来源给出的脚本骨架（已简化，检测逻辑需替换为你所用客户端的方式）：

#!/bin/bash
QUERIES_FILE="${1:?Usage: $0 <queries.json>}"
SKILL_NAME="my-skill"
RUNS=3

# 返回 0 表示技能被调用。这里以 Claude Code 的 JSON 输出为例，
# 其他客户端请替换为对应的日志/工具调用检测方式。
check_triggered() {
  local query="$1"
  claude -p "$query" --output-format json 2>/dev/null \
    | jq -e --arg skill "$SKILL_NAME" \
      'any(.messages[].content[]; .type == "tool_use" and .name == "Skill" and .input.skill == $skill)' \
      > /dev/null 2>&1
}

count=$(jq length "$QUERIES_FILE")
for i in $(seq 0 $((count - 1))); do
  query=$(jq -r ".[$i].query" "$QUERIES_FILE")
  should_trigger=$(jq -r ".[$i].should_trigger" "$QUERIES_FILE")
  triggers=0
  for run in $(seq 1 $RUNS); do
    check_triggered "$query" && triggers=$((triggers + 1))
  done
  jq -n --arg query "$query" --argjson should_trigger "$should_trigger" \
    --argjson triggers "$triggers" --argjson runs "$RUNS" \
    '{query: $query, should_trigger: $should_trigger, triggers: $triggers, runs: $runs, trigger_rate: ($triggers / $runs)}'
done | jq -s '.'

[本课程观点] 如果你使用的客户端没有脚本接口，用手工表格也能得到可用结论：每条查询跑 3 次，记录“加载了 SKILL.md / 没加载”，算比例。关键是固定查询、固定次数、记录证据，而不是凭印象。

[源站] 来源提示：如果客户端支持，一旦结果明确（已经咨询了技能，或已经开始不借助技能工作）就可以提前停止该次运行，节省时间与成本。

[源站] 触发率把“非确定性”变成可比较的数字，但它不是精确的准确率。三次运行只是一个小样本，0.33 与 0.67 的差别可能来自随机波动；当结论接近阈值时，应该增加运行次数或换一个模型再测。报告结果时，同时写出运行次数与触发次数，不要只写一个百分比。更重要的是记录“失败时发生了什么”：模型是没读描述、读了但判断无关，还是客户端没有扫描到技能。三种原因对应不同修法。

第三步：划分训练集与验证集

[源站] 如果拿所有查询来调描述，很容易过拟合：针对这些具体说法调好了，换一种说法就失效。来源建议：

  • 训练集约 60%：用来发现失败、指导修改。
  • 验证集约 40%：只用来检查改进是否泛化，不参与修改决策。
  • 两边都要有比例合理的正负例；随机打乱后固定划分，保证多轮比较的是同一组数据。

实现上可以分成 train_queries.json 与 validation_queries.json，分别运行脚本。[源站]（optimizing-descriptions.md）

[源站] 划分之后要“锁住”。把两个文件固定下来，不要在优化过程中把验证集里的查询挪到训练集，也不要根据验证集的失败去改描述。验证集的作用是模拟“上线后遇到的新说法”；一旦你用它指导修改，它就不再是独立检验。可以多轮使用同一个验证集来选版本，但不能用它调参。这个纪律比任何具体算法都重要。

[本课程观点] 把这一节放回真实任务检验：找一个会用到它的决定，写出遵守与不遵守两种做法，并指出不遵守时会出现什么可观察的错误。写不出具体错误，说明还需要更具体的场景、字段或命令。

第四步：五步优化循环

  1. 评估：当前描述在训练集与验证集上的触发率。
  2. 找失败：只看训练集——哪些正例没触发？哪些负例误触发？验证集结果不参与修改。
  3. 改描述：
    • 正例失败 → 可能太窄：扩大范围，补充“何时有用”的上下文。
    • 负例误触发 → 可能太宽：增加“不做什么”或与相邻能力的边界。
    • 不要直接塞入失败查询里的具体词，那是过拟合；找它代表的一般类别。
    • 改了几轮没进展，换一种结构/框架重写，而不是继续微调。
    • 检查 1024 字符上限，描述在优化中容易膨胀。
  4. 重复：直到训练集全部通过，或不再有实质提升。
  5. 选最佳版本：按验证集通过率选，而不是“最后一版”。早一点的版本可能泛化更好。

来源的实践建议：通常五轮就够；如果一直不提升，问题可能在查询集（太简单、太难、标注错误），而不是描述。[源站]（optimizing-descriptions.md）

[源站] 循环里最容易做错的是第三步“改描述”。看到正例失败，直觉是“把那个词加进去”；看到负例误触发，直觉是“把那个词排除掉”。这两种做法都会过拟合。更稳的思路是问：失败查询代表哪一类意图？描述是否缺少这类意图的覆盖？边界是否与相邻技能重叠？例如“老板要一张图”失败，不是缺“老板”这个词，而是缺少“用户描述需求但不点名工具”的场景。修的是类别，不是个例。

[源站] 当多轮微调没有进展时，换结构比继续改词更有效。可以尝试把描述从“能力清单 + 何时用”改成“用户意图 + 典型输入 + 明确边界”，或者反过来。不同框架会改变模型匹配的方式。换结构后仍然用同一套训练/验证集评估，才能比较。不要因为某一版在训练集上完美就停止；要看验证集是否也提升。

第五步：应用与最终检查

  1. 把选中的描述写回 SKILL.md 的 description。
  2. 确认长度 ≤1024 字符。
  3. 手动试几个提示，做快速 sanity check。
  4. 另写 5–10 条全新查询（正负混合），这些查询从未参与优化，用来做一次诚实检验。

[本课程观点] 最后一步很重要：它模拟“上线后遇到没见过的说法”。如果新查询表现明显差于验证集，说明前面的优化仍然过拟合。

[本课程观点] 应用阶段要防止“最后一次修改一定最好”的错觉。优化循环里，早一点的版本可能验证集通过率更高；选版本看验证集，不看你投入了多少轮。写回 SKILL.md 后，再跑一次格式校验与手动触发，确认没有把描述写坏。最后用一批全新查询做一次盲测：这些查询没有参与任何修改，能更诚实地反映泛化能力。如果新查询表现明显下降，说明前面的优化仍然过拟合。

[本课程观点] 把这一节放回真实任务检验：找一个会用到它的决定，写出遵守与不遵守两种做法，并指出不遵守时会出现什么可观察的错误。写不出具体错误，说明还需要更具体的场景、字段或命令。

记录什么

[本课程观点] 一个可复核的触发评估至少留下：

  • 查询集文件（含 should_trigger 标注）与训练/验证划分。
  • 每轮的描述版本（可用 git 记录，或复制到 iteration-N/description.txt）。
  • 每条查询 × 每次运行的结果。
  • 汇总表：正例通过数、负例通过数、训练/验证通过率。
  • 选择该版本的理由。

[本课程观点] 记录的目的不是交作业，而是让下一次修改有依据。最少要留下：查询集与标注、训练/验证划分、每轮描述版本、每条查询的运行结果、以及选择该版本的理由。没有这些，几周后你只会记得“当时调过”，却无法复现为什么。团队评审时，记录还能让评审者检查你是否用验证集调参，避免“看起来通过率很高，其实过拟合”的假象。

[本课程观点] 把这一节放回真实任务检验：找一个会用到它的决定，写出遵守与不遵守两种做法，并指出不遵守时会出现什么可观察的错误。写不出具体错误，说明还需要更具体的场景、字段或命令。

[本课程观点] 记录不需要复杂工具：一个表格加一个版本目录就够。关键是别人能根据记录复现你的判断，而不是只看到结论。

如果你只记住三件事

  1. 约 20 条查询，正负各半，负例优先用近邻；每条跑 3 次算触发率。
  2. 训练集调参，验证集只评估；固定划分，防止自欺。
  3. 按失败类型改描述（太窄/太宽），不要堆失败查询里的关键词。

练习

基础

[本课程观点] 为“PDF 表单填写”技能写 4 条查询：2 条应触发、2 条近邻负例。

提示与自检

[本课程观点] 正例示例：“帮我把这份申请表的姓名和日期填上”“这批表单能批量填吗，字段名在 Excel 里”。负例示例：“把这个 PDF 转成 Word”“提取这份 PDF 的目录”。负例应共享 PDF 概念但任务不同。

基础

[本课程观点] 回到本页第一个概念小节，用两三句话说明它解决什么问题，并举一个你工作中会遇到的例子。

提示与自检

[本课程观点] 合格答案要包含“问题—做法—具体场景”三部分；只复述小节标题，或举一个与本页无关的例子，都不算完成。

进阶

[本课程观点] 一条正例跑了 3 次，触发 1 次。触发率是多少？按 0.5 阈值算通过还是失败？下一步你会先检查什么？

提示与自检

[本课程观点] 0.33，失败。先检查：任务是否本来就不需要技能（简单一步请求）；描述是否缺少该说法；客户端是否可靠执行。不要立刻改描述——先排除前两类原因。

进阶

[本课程观点] 把本页的方法用到你自己的一个真实任务上，写出两条可执行指令和一个别人能照着做的验证方式。

提示与自检

[本课程观点] 两条指令要具体到字段、命令、阈值或判断标准；验证方式必须给出可观察的结果，例如某个文件存在、某条命令退出码为 0、某个字段等于期望值。

挑战

[本课程观点] 设计一次完整评估：20 条查询、训练/验证划分、每轮修改原则、停止条件、最终检验。说明你如何保证验证集没有被“偷看”。

评分点
  • 完整回应题目中的两个关键要求：2 分
  • 给出可验证的检查、示例或对照：2 分
  • 说明一个取舍、边界或失败情况：1 分
