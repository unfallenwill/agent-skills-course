触发与评估

S4 触发与评估

输出质量评估：断言、基线与迭代

把“看起来还行”变成可比较的证据：写评估用例、跑有/无 Skill 的对照、用断言与证据打分、比较通过率与成本。

阶段：S4 触发与评估 · 建议 45 分钟 · 先修：触发评估

[本课程观点] 触发正确，只说明技能被用上了；输出是否真的更好，还需要另一套证据。这一页把“看起来还行”变成可比较的数字：用例、断言、基线、通过率与成本。

一个评估用例包含什么

来源定义了三部分：提示（真实用户会输入的话）、预期输出（人类可读的成功描述）、输入文件（可选）。用例存放在技能目录下的 evals/evals.json。[源站]（evaluating-skills.md）

{
  "skill_name": "csv-analyzer",
  "evals": [
    {
      "id": 1,
      "prompt": "I have a CSV of monthly sales data in data/sales_2025.csv. Can you find the top 3 months by revenue and make a bar chart?",
      "expected_output": "A bar chart image showing the top 3 months by revenue, with labeled axes and values.",
      "files": ["evals/files/sales_2025.csv"],
      "assertions": [
        "The output includes a bar chart image file",
        "The chart shows exactly 3 months",
        "Both axes are labeled",
        "The chart title or caption mentions revenue"
      ]
    }
  ]
}

写提示的四个建议

  • 先写 2–3 个用例，看到第一轮结果后再扩展。不要在没跑过之前过度投入。
  • 变化说法：随意（“hey can you clean up this csv”）与精确（“Parse the CSV at data/input.csv, drop rows where column B is null, and write the result to data/output.csv”）都要有。
  • 覆盖边界：至少一个畸形输入、异常请求或指令可能歧义的情况。
  • 使用真实上下文：文件路径、列名、个人背景；“处理这个数据”太空泛，测不出什么。

[源站]（evaluating-skills.md）

[源站] 三部分里，“预期输出”最容易被写空。不要写“输出良好”，要写可观察的结果：文件存在、字段齐全、图表有标签、行数正确、错误被拒绝。输入文件也要真实：用脱敏后的实际数据，而不是手工构造的完美样例。只有真实输入才能暴露编码、缺失值、格式不一致这些常见问题。用例不用多，先写两三个能覆盖主路径与一个边界的，跑完再扩展。

[本课程观点] 把这一节放回真实任务检验：找一个会用到它的决定，写出遵守与不遵守两种做法，并指出不遵守时会出现什么可观察的错误。写不出具体错误，说明还需要更具体的场景、字段或命令。

运行：有技能 vs 无技能

核心模式是每个用例跑两遍：一次带技能，一次不带技能（或带上一版本）。这给你一个对照基线。改进已有技能时，先快照当前版本，把基线指向快照，输出存到 old_skill/ 而不是 without_skill/。[源站]

[源站] 每次运行都应在干净上下文中开始，不带上一轮的残留，也不带技能开发过程的记忆。支持子代理的客户端天然满足；否则每个用例用独立会话。

csv-analyzer-workspace/
└── iteration-1/
    ├── eval-top-months-chart/
    │   ├── with_skill/
    │   │   ├── outputs/
    │   │   ├── timing.json
    │   │   └── grading.json
    │   └── without_skill/
    │       ├── outputs/
    │       ├── timing.json
    │       └── grading.json
    ├── eval-clean-missing-emails/
    │   └── ...
    └── benchmark.json

[源站] 目录结构不是硬性规定，但“每轮一个目录、每用例有对照、结果可追溯”值得保留。否则几轮之后你会分不清哪个结果对应哪个版本。

同时记录成本

[源站] 技能可能显著提升质量，也可能把 token 用量翻三倍。来源建议每次运行记录 token 数与耗时：

{
  "total_tokens": 84852,
  "duration_ms": 23332
}

在 Claude Code 中，子任务完成通知会带上 total_tokens 与 duration_ms，要立即保存，因为它们不会持久化到别处。[源站]

[源站] 没有基线，就无法判断技能是否真的有价值。模型本身可能已经能完成 60% 的任务，技能把它提升到 80%，这是有价值的；如果无技能也能达到 80%，技能可能只是增加了成本。基线还可以帮助你区分“技能变好”与“模型这次状态好”。每次比较都应在相同模型、相同输入、相同运行次数下进行；否则差异无法归因。对照不是形式，而是判断收益的唯一方法。

断言：把“好”拆成可检查的句子

[源站] 断言是对输出应包含或达成什么的可验证陈述。来源建议先看第一轮输出，再写断言——你往往在看到结果之前，并不知道“好”具体长什么样。

强断言弱断言原因
输出文件是合法 JSON输出很好前者可程序化验证，后者无法评分
柱状图有带标签的坐标轴图表使用精确短语 “Total Revenue: $X”前者具体可观察；后者过于脆弱，正确但措辞不同的输出会失败
报告至少包含 3 条建议报告看起来专业前者可计数，后者依赖主观印象

不是所有质量都能拆成断言。写作风格、视觉设计、“感觉对不对”更适合人工评审。断言留给能客观检查的东西。[源站]

[源站] 写断言时，先问“这条能不能由另一个人从输出中检查”。能，就写成可观察的陈述；不能，就交给人工评审。断言不应该依赖模型的自我评价，也不应该要求特定措辞，除非措辞本身就是业务要求。一个用例的断言不必覆盖所有质量维度：机械检查用脚本，结构检查用计数，语义质量用人工或盲评。分工清楚，评分才稳定。

[本课程观点] 把这一节放回真实任务检验：找一个会用到它的决定，写出遵守与不遵守两种做法，并指出不遵守时会出现什么可观察的错误。写不出具体错误，说明还需要更具体的场景、字段或命令。

评分：PASS / FAIL 加证据

[源站] 逐条评估断言，记录 PASS 或 FAIL，并附具体证据：引用输出内容或指出文件，而不是只给结论。

{
  "assertion_results": [
    { "text": "The output includes a bar chart image file", "passed": true,
      "evidence": "Found chart.png (45KB) in outputs directory" },
    { "text": "Both axes are labeled", "passed": false,
      "evidence": "Y-axis is labeled 'Revenue ($)' but X-axis has no label" }
  ],
  "summary": { "passed": 3, "failed": 1, "total": 4, "pass_rate": 0.75 }
}

[源站] 评分原则：PASS 必须有具体证据，不要给“情有可原”的通过；一个标题叫“Summary”但只有一句空话的小节，应判 FAIL。同时复查断言本身：太容易（总是通过）、太难（总是失败）、无法从输出验证的，都要在下一轮修正。（evaluating-skills.md）

[源站] 机械性检查（JSON 合法、行数正确、文件存在）优先用脚本，而不是让 LLM 判断；脚本更可靠，也能跨轮复用。主观质量可以用“盲评”：把两个版本的输出匿名交给评审者，不告知来源，减少偏见。

[源站] PASS 必须附证据，是为了防止“看起来差不多”被当成通过。证据可以是文件路径、输出片段、计数结果或截图；关键是别人能根据证据复核。FAIL 也要写清缺什么，否则下一轮不知道该修技能还是修断言。评分时还要复查断言本身：如果一条断言无论有无技能都通过，它没有区分度；如果无论怎么改都失败，可能断言写错了。评分不是给模型打分，而是给“技能是否解决了一个具体问题”提供证据。

汇总：通过率、时间、token 与差值

[源站] 每轮结束后，按配置汇总统计，写入 benchmark.json：

{
  "run_summary": {
    "with_skill": {
      "pass_rate": { "mean": 0.83, "stddev": 0.06 },
      "time_seconds": { "mean": 45.0, "stddev": 12.0 },
      "tokens": { "mean": 3800, "stddev": 400 }
    },
    "without_skill": {
      "pass_rate": { "mean": 0.33, "stddev": 0.10 },
      "time_seconds": { "mean": 32.0, "stddev": 8.0 },
      "tokens": { "mean": 2100, "stddev": 300 }
    },
    "delta": { "pass_rate": 0.50, "time_seconds": 13.0, "tokens": 1700 }
  }
}

差值告诉你技能的成本与收益：多花 13 秒、通过率提升 50 个百分点，通常值得；token 翻倍但只提升 2 个百分点，可能不值得。早期用例少时，先看原始通过数与差值，标准差在样本扩大后才更有意义。[源站]

[源站] 汇总时不要只报一个平均通过率。至少要分开报告有技能/无技能、每个用例的通过情况、以及 token 与耗时。平均值会掩盖极端值：一个用例从 0 到 1，另一个从 1 到 0，平均可能不变，但技能的实际价值完全不同。把每个用例的变化列出来，才能看到技能在哪些场景有效、哪些场景无效。成本也要分用例看，异常值往往指向某个具体步骤的低效。

[本课程观点] 把这一节放回真实任务检验：找一个会用到它的决定，写出遵守与不遵守两种做法，并指出不遵守时会出现什么可观察的错误。写不出具体错误，说明还需要更具体的场景、字段或命令。

看模式，而不是只看总数

  • 两边都总是通过的断言：没有信息量，模型不用技能也能做；删掉或替换，否则会虚高“有技能”的通过率。
  • 两边都总是失败的断言：断言本身有错、用例太难，或检查了错误的东西；下一轮前修复。
  • 有技能通过、无技能失败的断言：技能真正增值的地方。弄清楚是哪条指令或脚本起了作用。
  • 同一条用例时过时不过（高标准差）：可能是不稳定用例，也可能是指令歧义导致模型每次理解不同；加示例或更具体的指导。
  • 时间/token 异常值：某条用例耗时是其他三倍，去读完整执行记录找瓶颈。

[源站]（evaluating-skills.md）

[源站] 模式分析的目标是“找到技能真正增值的地方”。“有技能通过、无技能失败”的断言最有价值，它说明某条指令或脚本改变了结果；追查是哪一条，能帮你保留有效内容、删掉无效内容。“两边都通过”的断言没有区分度，应该删掉或换成更难的边界；“两边都失败”的断言可能是断言本身有问题，也可能是任务超出当前能力。不要为了让报告好看而保留无信息量的断言。

人工评审不可省

[源站] 断言只能检查你想到的东西。人工评审能发现：技术上正确但没抓住重点、格式合规但不可用、以及难以表达为 pass/fail 的质量问题。逐用例看实际输出与评分，记录具体反馈：

{
  "eval-top-months-chart": "The chart is missing axis labels and the months are in alphabetical order instead of chronological.",
  "eval-clean-missing-emails": ""
}

“缺少轴标签”是可行动的反馈；“看起来不好”不是。空字符串表示该用例通过人工评审。[源站]

[源站] 人工评审要带着具体问题看输出：它是否解决了用户的真实目标？结构是否让读者能快速找到答案？有没有技术上正确但业务上不可用的地方？反馈要写成可修改的句子，例如“图表缺少单位，无法判断量级”，而不是“看起来一般”。评审者不需要重写技能，只需要指出“哪里不满足预期、为什么”。这些反馈会和失败断言、执行轨迹一起，成为下一轮修改的输入。

[本课程观点] 把这一节放回真实任务检验：找一个会用到它的决定，写出遵守与不遵守两种做法，并指出不遵守时会出现什么可观察的错误。写不出具体错误，说明还需要更具体的场景、字段或命令。

迭代：三类信号，四条原则

[源站] 三类信号：失败断言指向具体缺口；人工反馈指向更广的质量问题；执行记录揭示为什么——指令被忽略可能是歧义，浪费步骤可能是指令该删。

[源站] 把三类信号连同当前 SKILL.md 交给 LLM，请它提出修改。来源给出的四条原则：

  1. 从反馈中泛化。 技能会在许多不同提示上使用，修复应针对底层问题，而不是给具体例子打补丁。
  2. 保持精简。 更少、更好的指令往往胜过大而全；如果加了规则通过率仍不升，可能是过度约束，试着删。
  3. 解释原因。 “做 X，因为 Y 容易导致 Z”比“永远做 X、绝不 Y”更容易被稳定遵循。
  4. 打包重复工作。 如果每次运行都在重写同一段辅助逻辑（画图、解析、校验），把它写成脚本放进 scripts/。

循环：提出改进 → 应用 → 在新 iteration-N+1/ 重跑全部用例 → 评分汇总 → 人工评审 → 重复。当结果满意、反馈持续为空，或不再有实质提升时停止。[源站]（evaluating-skills.md）

[本课程观点] 把这一节放回真实任务检验：找一个会用到它的决定，写出遵守与不遵守两种做法，并指出不遵守时会出现什么可观察的错误。写不出具体错误，说明还需要更具体的场景、字段或命令。

如果你只记住三件事

  1. 评估用例 = 提示 + 预期输出 +（可选）输入文件；每例跑有/无技能两遍。
  2. 断言要可验证、可计数、不过度依赖措辞；PASS 必须附证据。
  3. 看通过率差值、成本差值与失败模式；按底层问题改，不要给个例打补丁。

练习

基础

[本课程观点] 判断断言强弱：（A）输出包含一个 CSV 文件；（B）输出令人满意；（C）摘要不超过 200 字。

提示与自检

[本课程观点] A 强（文件存在且扩展名可查）；B 弱（无法评分）；C 强（可计数，但需确认“不超过”是硬要求）。

基础

[本课程观点] 回到本页第一个概念小节，用两三句话说明它解决什么问题，并举一个你工作中会遇到的例子。

提示与自检

[本课程观点] 合格答案要包含“问题—做法—具体场景”三部分；只复述小节标题，或举一个与本页无关的例子，都不算完成。

进阶

[本课程观点] 为“会议纪要转行动项”写 3 个评估用例（含 1 个边界），每个至少 2 条断言。

提示与自检

[本课程观点] 边界可以是“会议中没有明确负责人”或“录音含两人重叠发言”。断言示例：“输出包含负责人列”“无负责人时写‘待定’而非编造姓名”“行动项数量与记录中的决策数一致”。断言应可从输出直接检查。

进阶

[本课程观点] 把本页的方法用到你自己的一个真实任务上，写出两条可执行指令和一个别人能照着做的验证方式。

提示与自检

[本课程观点] 两条指令要具体到字段、命令、阈值或判断标准；验证方式必须给出可观察的结果，例如某个文件存在、某条命令退出码为 0、某个字段等于期望值。

挑战

[本课程观点] 设计一次两轮迭代：第一轮 3 个用例，第二轮扩展到 6 个；给出 benchmark 表头、停止条件，并说明如何处理“两边都通过”的断言。

评分点
  • 完整回应题目中的两个关键要求：2 分
  • 给出可验证的检查、示例或对照：2 分
  • 说明一个取舍、边界或失败情况：1 分
